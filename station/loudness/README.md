# Нормализатор громкости эфира

Станция subwave умеет выравнивать громкость сама: при отдаче трека в Liquidsoap
контроллер ставит ему `liq_amplify` к цели `loudness.targetLufs` (−14 LUFS,
подъём не больше `maxBoostDb` = 6 dB и не выше потолка пика −1 dBFS). Цифру он
берёт из ReplayGain в тегах (через Navidrome), иначе из `tracks.loudness_lufs`
в `library.db`.

**До 2026-09-23 не было ни того, ни другого.** Тегов ReplayGain в коллекции нет,
анализатор станции колонку не заполнял — у всех 4631 треков `loudness_lufs`
пуст, и каждый играл с усилением 1. Перепады громкости между треками шли
отсюда, а не от настройки.

## Как устроено

| Шаг | Где | Что |
|---|---|---|
| [`measure.py`](measure.py) | GPU-хост | ffmpeg `ebur128` по каждому файлу **целиком**: integrated LUFS и true peak. Кэш — JSON на шаре (`LOUDNESS_GPU_CACHE`). Повторный запуск меряет только новые и изменившиеся файлы (размер + mtime) |
| [`apply.py`](apply.py) | хост станции | тот же кэш с шары (`LOUDNESS_STATION_CACHE`), путь → id станции через базу Navidrome (`media_file.path`), запись `loudness_lufs` / `peak_db` в `library.db` одной транзакцией |
| [`run.py`](run.py) | рабочая машина | оба шага подряд; скрипты копируются на хосты перед каждым запуском, поэтому разошедшейся копии не бывает. Адреса, пути и SSH — из `station/.env` (шаблон — `station/.env.example`) |

```bash
python station/loudness/run.py --dry-run     # замерить, в базу станции не писать
python station/loudness/run.py               # замерить и записать
```

**Почему замер, а не ReplayGain в тегах.** Разметка тегами (`rsgain`) переписала
бы 4631 файл, а коллекцию раздаёт Syncthing с хоста станции (папка `Music`,
`sendonly`): правка каждого файла ушла бы на все связанные устройства. Замер
живёт в базе станции и коллекцию не трогает.

**Почему по файлу целиком.** Анализатор subwave меряет только начало трека
(`ANALYZE_SECONDS`), и тихое вступление громкой песни дало бы ей лишний
подъём. Пик — true peak: он не меньше выборочного, поэтому потолок подъёма
выходит осторожнее, а не смелее.

**Почему ffmpeg на GPU-хосте.** Коллекция лежит там на локальном диске (41.7 ГБ не
надо гнать по SMB), и ffmpeg в сети живёт только там. Первый прогон — 37 минут
на 8 процессов с пониженным приоритетом; догон на неизменной коллекции — около
секунды.

**Неполный обход не отменяет запись.** Недоступная ветвь или файл, исчезнувший между
обходом и `stat`, — это `walk_errors` в итоге `measure.py` и код выхода **3**: всё
видимое измерено, а чистка кэша пропущена (недоступное неотличимо от удалённого).
`run.py` на этом коде всё равно выполняет `apply.py`, печатает итог и только потом
выходит с кодом 1 и предупреждением — ночная задача падает, но замеры уже в базе
станции. До 2026-10-09 такой обход давал код 1, и `run.py` выходил до записи:
постоянная ошибка обхода молча выключала выравнивание всех новых треков. Код 1 у
`measure.py` по-прежнему значит упавший замер (нет диска, чужой кэш) — тогда
записи нет.

## Что вышло (2026-09-23)

| | До | После |
|---|---|---|
| Медиана коллекции | −10.0 LUFS | −14.0 LUFS |
| Разброс, стандартное отклонение | 3.6 LU | 1.3 LU |
| Разброс p10–p90 | 8.4 LU | 0.9 LU |

Срезано 3925 треков, поднято 343. 629 треков тише цели, но поднять их не дал
собственный пик: у 3249 файлов true peak выше 0 dBTP. Типичный трек стал тише на
4 dB — это цена выравнивания к −14 LUFS, общепринятой цели стриминга.

**Не читается один файл коллекции:** тег ID3 цел, звуковые данные ffmpeg не
распознаёт («Invalid data found»). Это порча в коллекции; трек играет без выравнивания.

## Голос ведущей: громче музыки на ~2 dB

**Правило владельца: голос ведущей громче музыки** — примерно на 2 dB выше
медианы музыки. При музыке, выровненной к −14 LUFS, это около −12 LUFS голоса на
выходе голосовой цепочки Liquidsoap. Ручка `tts.gainDb` — следствие правила: сменится
движок TTS или цель музыки — пересчитать от правила, а не переносить число.

Первый подбор 2026-09-23 это правило нарушил. Ориентиром взяли «сохранить прежний
баланс» — голос на 0.9 dB **тише** медианы невыровненной музыки, как выходило
при +9 (ручки −4 для Chatterbox и −3 для F5). Владелец услышал тихий голос:
громкость он поднимал (0 → +6 → +9) именно затем, чтобы голос был громче музыки,
а «на 0.9 dB тише» было тем, чего он успел добиться, а не тем, чего хотел.

**Подбирать по выходу цепочки, а не на глаз.** Реплика проходит в Liquidsoap
компрессор `mic_chain` (4:1 выше −18 dBFS, +7 dB, ×1.4), и сдвиг `gainDb` на входе
доходит до эфира примерно вчетверо слабее. [`voice_chain.py`](voice_chain.py)
моделирует цепочку в ffmpeg. Клипы для подбора сперва проверять на речь
(`station/tts-f5/tools/check_speech.py`, whisper со сверкой слов): у шипения
громкость, частота и длительность такие же, как у речи, и первый замер F5 был
снят именно на нём.

| `gainDb` | F5 (сырой −18.9 LUFS) | Chatterbox (сырой −17.35 LUFS) |
|---|---|---|
| −4 | −15.6 | −14.9 |
| 0 | −13.8 | −13.4 |
| +4 | −12.6 | −12.2 |
| +5 | **−12.3** | −11.9 |
| +6 | −12.0 | −11.6 |

Сейчас в эфире F5 и `tts.gainDb.remote = +5` — −12.3 LUFS, на ~1.7 dB громче музыки.
Правило давало +6 (ровно −12,
[`patches/2026-09-23-voice-louder-than-music.json`](../onboard/patches/2026-09-23-voice-louder-than-music.json)),
но вечером 23.09 владелец сам попросил +5
([`patches/2026-09-23-voice-gain-5.json`](../onboard/patches/2026-09-23-voice-gain-5.json)) —
его слово важнее расчёта, обратно не поднимать.
При откате на Chatterbox ручку опустить до **+5** (−11.9). piper остался на −4 от
прежнего ориентира: в эфир он не выходит — запасной движок запрещён
(`tts.fallback.enabled = false`), — но если его вернут, пересчитать по правилу.

Клипы для повторного подбора — `<share>\music\voice-chain-2026-09-23\`
(Chatterbox) и `…\voice-chain-f5v1-2026-09-23\` (F5).

## Новые треки

Ночная задача планировщика (у нас — ежедневно в 05:40) запускает
`python station/loudness/run.py` и догоняет замеры. Но **строку в `library.db` новый
трек получает только после сверки станции с Navidrome** (Admin → Library →
Reconcile, `POST /api/library/reconcile`): до неё писать замер некуда, и трек
играет без выравнивания. Сверку ночная задача сознательно не делает: она удаляет
строки треков, которых Navidrome не вернул, и сбой монтирования шары унёс бы
вместе с ними дорогую разметку настроений.

Порядок после пополнения коллекции: Navidrome пересканировал (сам, раз в 15
минут) → сверка в админке станции → `python station/loudness/run.py` (или ночная
задача).

## Кто ещё пишет в эти колонки

Анализатор станции (`POST /api/tag-library` с `analyze: true`) перепишет
`loudness_lufs` своим замером по началу трека. Следующий прогон нормализатора
вернёт замер по файлу целиком: значения расходятся, и строка обновится.

`apply.py` отказывается писать, если замера нет больше чем у половины треков
станции: так выглядит не пополнение, а разошедшаяся схема путей или чужой кэш.
