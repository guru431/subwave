# TTS на GPU gpu-host

Тяжёлый синтез вынесен на машину с картой: RTX 5060 Ti (16 ГБ), `<gpu-host>`.
На Debian остаётся только лёгкое и постоянно работающее.

**С 2026-10-09 мостик и F5 живут на srvllm** — разделы ниже описывают прежнюю площадку. Мостик —
контейнер `tts-bridge` шага `interim` проекта llm_routers (`/opt/ai/interim/compose.yaml`, образ
vLLM ради Python): код — побайтовая копия `bridge.py` в `/opt/ai/interim/tts-bridge/`,
`UPSTREAM=http://f5-tts:4126`, `GPU_CTL_URL` не задан — аренды слота нет, её код молчит.
Выкатка — копия файла (`install` с прежними владельцем и правами) и `docker restart tts-bridge`,
перерыв — пара секунд. Проверка — `/health` и `POST /speak` с несуществующим голосом: в ответе
`X-TTS-Voice-Used` и `X-TTS-Fell-Back*`. Сборка и смена образа F5 —
[tts-f5/README.md](../tts-f5/README.md), «На srvllm».

## Что развёрнуто

| Что | Где | Порт |
|---|---|---|
| Chatterbox TTS API (`travisvn/chatterbox-tts-api`, профиль **blackwell**) | `<gpu-data>\_task\LLM\chatterbox-tts` на gpu-host | `4123` |
| Мостик Remote-контракта subwave ([`bridge.py`](bridge.py)) | там же | `4124` |

Образ выбран не по вкусу, а по двум жёстким требованиям спеки:

- **многоязычный чекпойнт** (`USE_MULTILINGUAL_MODEL=true`, 22 языка, включая русский) —
  базовый Chatterbox англоязычный, и вердикт «движок не годится» был бы вынесен не тому;
- **CUDA ≥ 12.8 / PyTorch cu128** — RTX 5060 Ti это Blackwell, compute capability 12.0.
  `docker/Dockerfile.blackwell` собирается на `nvidia/cuda:12.8.1-runtime-ubuntu22.04`
  и ставит `torch==2.7.0 … --index-url https://download.pytorch.org/whl/cu128`.
  `nvidia-smi` внутри контейнера этого не подтверждает: он читает драйвер хоста и печатает
  карту при любой версии CUDA в образе. Проверка ядер — `torch.cuda.get_device_capability()`
  и реальное вычисление на устройстве.

## Грабля gpu-host: `docker pull` не работает из SSH

Docker Desktop живёт в пользовательской сессии, а SSH — это session 0. Кредхелпер
(`credsStore: desktop`) там падает:

```
error getting credentials — `A specified logon session does not exist.`
```

**Правкой конфига не лечится** — проверено в `_boss/gpu-ctl/deploy/wipe-and-reinstall.md`:
удаление `credsStore`, пустое значение, `--config` и `DOCKER_CONFIG` на чистый каталог
дают ту же ошибку, CLI Docker Desktop зовёт хелпер независимо от конфига.

Рабочее правило той же записи: **тянуть образы в session 2, запускать в session 0.**
Сборка и загрузка делаются временной задачей планировщика с `LogonType Interactive`:

```powershell
$a = New-ScheduledTaskAction -Execute "powershell.exe" `
     -Argument "-NoProfile -ExecutionPolicy Bypass -File <gpu-data>\_task\LLM\chatterbox-tts\build.ps1"
$p = New-ScheduledTaskPrincipal -UserId "Administrator" -LogonType Interactive -RunLevel Highest
Register-ScheduledTask -TaskName "TmpChatterboxBuild" -Action $a -Principal $p -Force
Start-ScheduledTask -TaskName "TmpChatterboxBuild"
# ... по завершении:
Unregister-ScheduledTask -TaskName "TmpChatterboxBuild" -Confirm:$false
```

Локально лежащий образ из session 0 запускается нормально — `docker run`/`compose up`
после предзагрузки работают по SSH.

Запуск мостика (образ тот же, отдельный не нужен — в нём уже есть Python):

```powershell
docker run -d --name chatterbox-bridge --restart unless-stopped `
  --network docker_default -p 4124:4124 -e PORT=4124 `
  -e UPSTREAM=http://chatterbox-tts:4123 `
  -e GPU_CTL_URL=http://host.docker.internal:8119 `
  -e GPU_CTL_TOKEN=<GPU_CTL_TOKEN из vault _boss> `
  -v <gpu-data>\_task\LLM\chatterbox-tts\bridge:/bridge `
  docker-chatterbox-tts:latest python /bridge/bridge.py
```

`GPU_CTL_*` — аренда слота на пульте GPU (`_boss/gpu-ctl`, :8119). Карта на gpu-host
одна на шесть слотов, и слот **без аренды пульт вправе погасить в любой момент**, в
том числе на середине синтеза фразы: TTS ходил на `:4123` напрямую, `/ensure-up` не
звал, и аренды у него не бывало никогда. С 2026-08-29 мостик берёт слот перед каждым
синтезом — заодно продлевая аренду, пока идёт диалог. Без этих переменных мостик
работает как раньше, а недоступный пульт синтез не блокирует (молчащий TTS хуже, чем
TTS без аренды).

**Аренду просит и неудачный `/health`** (с 2026-10-09). Гейт C05 контроллера не шлёт
`/speak`, пока `/health` мостика отвечает 503: движок «заведомо лежит», и реплику не
генерируют впустую. Но до этой страховки аренду брал только `/speak`, и выгнанный
пультом слот `tts` будили именно ошибочные `/speak` — с гейтом их нет, и поднять слот
осталось бы одному Restore-Residents пульта. Поэтому `/health`, не дождавшись готовности upstream,
сам зовёт `/ensure-up`: в фоновом потоке (ответ 503 аренды не ждёт), не чаще раза в
`HEALTH_LEASE_EVERY` секунд (60) и не больше одного потока разом. И только пока
станция говорит — в `HEALTH_LEASE_WINDOW` секунд (1800) после последнего `/speak`:
контроллер спрашивает `/health` раз в 30 с и ночью без слушателей, и без окна
выгнанный слот будился бы круглые сутки. Позже окна слот поднимает только пульт.
Без `GPU_CTL_URL` этого нет, как и прочей аренды.

`-e PORT=4124` обязателен: в образе Chatterbox уже задан `PORT=4123`, и без явного
переопределения мостик поднимется на 4123 внутри контейнера, а опубликован будет 4124 —
снаружи не ответит никто, а в логе при этом будет бодрое `bridge: :4123`.

## Контейнером распоряжается пульт gpu-ctl (с 2026-08-25)

`chatterbox-tts-api-blackwell` объявлен слотом `chatterbox` в
`_boss/gpu-ctl/slots.json` (класс `resident`, 4.25 ГБ, холодный старт 29 с). Это
значит: **пульт вправе погасить контейнер**, когда карта нужна под `llm` или `image`,
и поднимает его обратно сам, как только место освобождается.

Повод — не порядок ради порядка: пока TTS был неучтённым, он занимал 4353 МиБ, которых
не хватало модели `gemma4:12b`, и сутки ночных задач `openclaw` падали. Пульт вычитал
эту память из свободного (он считает по живому `nvidia-smi`), но погасить контейнер
не мог — в декларации его не было. Разбор:
`_boss/wiki/projects/boss/incident-chatterbox-undeclared-slot-2026-08-25.md`.

Практические следствия для этого проекта:

- перерыв в TTS до ~29 с, когда пульт поднимает слот обратно;
- ~~синтез может оборваться на середине: аренды у слота нет, потому что мостик ходит на
  `:4123` напрямую и `/ensure-up` не зовёт~~ — **исправлено 2026-08-29**: мостик берёт
  слот перед каждым синтезом (см. выше). Строка оставлена зачёркнутой, потому что на неё
  ссылается закрытая находка P3 в `_boss/FINDINGS.md`;
- **контейнер не пересоздавать через `compose down/up`** — пульт ведёт его как
  `docker start/stop` по имени; `compose down` снесёт заодно `chatterbox-bridge`,
  который носит те же compose-метки.

```powershell

  -Protocol TCP -LocalPort 4123,4124 -Profile Any
```

## Автозапуск: отдельная таска не понадобилась

План предписывал таску `logon_type: interactive` + `trigger: AtLogOn` в
`_boss/cron/registry.yaml`. По факту то же самое обеспечивают два уже существующих
механизма: Docker Desktop стартует при логоне (Run-ключ в HKU профиля Administrator),
а оба контейнера подняты с `--restart unless-stopped`, поэтому демон возвращает их сам.
Таска добавила бы третий движущийся элемент, делающий ровно это же.

Причина, по которой Password-таска не годится, остаётся в силе и записана здесь на
случай, если автозапуск когда-нибудь понадобится явный: до логона демона Docker Desktop
нет вовсе, и такая таска упала бы на `docker: error during connect`.

**Следствие принимается осознанно: до логона на gpu-host TTS недоступен.** Проверка после
ближайшей перезагрузки gpu-host — `docker ps` показывает `chatterbox-tts-api-blackwell`
и `chatterbox-bridge`, а `curl http://<gpu-host>:4124/health` с Debian отдаёт `{"ok": true}`.

**Чего эти два механизма не покрывают — зависший бэкенд Docker Desktop** (2026-09-20).
Пользователь был залогинен, процессы `Docker Desktop` и `com.docker.backend` висели в
памяти с 15.09, дистрибутив `docker-desktop` в WSL значился `Running` — но движок отдавал
`500 Internal Server Error` на **оба** пайпа (`dockerDesktopLinuxEngine` и `docker_engine`),
и вместе с ним лежали все контейнеры машины: Chatterbox, мостик, `ollama`, OCR. `--restart
unless-stopped` здесь бесполезен — некому перезапускать, демон сам и есть отказавший.

Снаружи это выглядело как молчащий TTS: станция штатно деградировала на piper и шла в
эфир дальше, поэтому отказ мог держаться неделями. Восстановление — перезапуск Docker
Desktop **в интерактивной сессии** (по SSH из session 0 процесс не стартует, тот же
барьер, что у `docker pull`), временной задачей планировщика:

```powershell
$cmd = 'Start-Process -FilePath "C:\Program Files\Docker\Docker\Docker Desktop.exe"'
$enc = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($cmd))
$a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument "-NoProfile -ExecutionPolicy Bypass -EncodedCommand $enc"
$p = New-ScheduledTaskPrincipal -UserId 'Administrator' -LogonType Interactive -RunLevel Highest
Register-ScheduledTask -TaskName 'TmpDockerRestart' -Action $a -Principal $p -Force
Start-ScheduledTask -TaskName 'TmpDockerRestart'
# ... по завершении:
Unregister-ScheduledTask -TaskName 'TmpDockerRestart' -Confirm:$false
```

`-EncodedCommand` здесь не украшение: путь с пробелами внутри `-Argument`, проходящий
через SSH и PowerShell, теряет экранирование и задача падает с `LastTaskResult = 1`,
убив старые процессы и не подняв новые. Контейнеры после подъёма демона возвращаются
сами (`--restart unless-stopped`), мостик отвечает `{"ok": true}` примерно через минуту.

## Запасной движок: русский голос Piper доложен вручную

**Следствие принимается осознанно: до логона на gpu-host TTS недоступен.** Поэтому запасной
движок в subwave обязателен. Piper и Kokoro действительно встроены в образ контроллера,
но **русского голоса в образе не было ни у одного из них**: у Piper лежал единственный
`en_GB-alan-medium`, список Kokoro (54 голоса) покрывает en/es/fr/hi/it/ja/pt/zh.
Проверено на живом стенде 2026-08-23: при остановленном мостике поток не прерывался —
контроллер синтезировал **русский текст английским голосом**.

Каталог голосов вынесен на хост и в него доложен `ru_RU-dmitri-medium`
(`rhasspy/piper-voices` на HuggingFace, 63 МБ). Монтирование и порядок сборки каталога —
в [`deploy/docker-compose.override.yml`](../deploy/docker-compose.override.yml);
выбор голоса — `PIPER_VOICE` / `PIPER_VOICE_CONFIG` в `.env` рядом с compose.

**Английский голос копируется в тот же каталог обязательно:** том подменяет
`/opt/piper/voices` целиком, и без копии персона с англоязычным голосом потеряет файл.

Проверка отказоустойчивости (2026-08-23, мостик остановлен на 5 минут):

| Что смотрели | Результат |
|---|---|
| Прямой синтез русской фразы в контейнере | 2.9 с аудио, RTF 0.127 — Piper успевает на CPU с восьмикратным запасом |
| Реакция контроллера | `[remote] TTS endpoint unavailable`, эфир не прервался |
| Чей голос звучал | файлы в `state/voice` — **22050 Гц** (Piper) против 24000 Гц (Chatterbox) до остановки |
| Возврат мостика | `[remote] TTS endpoint available`, все шесть контейнеров `healthy` |

Частота дискретизации — самый дешёвый способ отличить движки постфактум: строки
«falling back to piper» контроллер в лог не пишет.

## Английский акцент у русского ведущего: библиотека голосов была пуста

Симптом — русский текст читался с сильным английским акцентом. Причина не в ударениях:
Chatterbox это **zero-shot клонирование**, и клонирует он не только тембр, но и акцент
диктора из эталонного сэмпла. Библиотека голосов была пуста (`GET /voices` →
`{"voices":[],"count":0}`), поэтому синтез шёл с дефолтного `/app/voice-sample.mp3` —
английского, — а язык многоязычной модели берётся **исключительно из метаданных
голоса**, так что все ветки выбора сводились к `en`.

Чинится в два шага, и **оба обязательны**.

```bash
# 1. эталон русской речи — 10–20 с; берётся у piper, он уже стоит запасным движком
sudo docker exec sub-wave-controller sh -c \
  'piper --model $PIPER_VOICE --config $PIPER_VOICE_CONFIG --output_file /tmp/ru-ref.wav' <<< "Добрый вечер. Это AI радио…"
sudo docker cp sub-wave-controller:/tmp/ru-ref.wav /tmp/ru-ref.wav

# 2. загрузка в библиотеку — language=ru здесь и есть весь смысл операции
curl -X POST http://<gpu-host>:4123/voices \
  -F voice_name=ru-dmitri -F language=ru -F 'voice_file=@/tmp/ru-ref.wav;type=audio/wav'
curl -X POST http://<gpu-host>:4123/voices/ru-dmitri/aliases -F alias=alloy   # страховка, form-data а не JSON
```

**Второй шаг — прописать голос персоне**, иначе первый бесполезен: у `p_ru` поле
`tts.voice` было пустой строкой, а мостик пробрасывает только **непустой** `voice`.
Задаётся целиком, потому что `patch_persona` сливает верхнеуровневые ключи и частичный
объект `tts` затёр бы соседние поля:

```bash
echo '{"tts":{"engine":"remote","cloudProvider":"openai","voice":"ru-dmitri","gainDb":0,"speed":1}}' > /tmp/voice.json
python3 station/onboard/onboard.py --persona p_ru --from /tmp/voice.json
```

**`POST /voices/default` проблему не решает** — при пустом `voice` код возвращает
дефолтный сэмпл и `en`, не заглядывая в библиотеку. Именно поэтому нужен непустой голос
у персоны, а не дефолт на сервере.

Проверка (2026-09-21): `POST :4124/speak` с `voice=ru-dmitri` отдал 311 118 байт,
**24000 Гц** — то есть озвучил Chatterbox, а не откатившийся piper (у него 22050).

### Женский голос

Голос ведущего — это целиком эталонный клип, поэтому смена пола не трогает ни код, ни
движок: берётся другой образец и кладётся в библиотеку рядом. Русских голосов у piper
четыре — `denis`, `dmitri`, `ruslan` (мужские) и **`irina`** (женский, только `medium`).

```bash
B=https://huggingface.co/rhasspy/piper-voices/resolve/main/ru/ru_RU/irina/medium
D=<deploy-dir>/subwave/piper-voices          # том, смонтированный в /opt/piper/voices
sudo curl -sL -o $D/ru_RU-irina-medium.onnx      $B/ru_RU-irina-medium.onnx
sudo curl -sL -o $D/ru_RU-irina-medium.onnx.json $B/ru_RU-irina-medium.onnx.json
# дальше — те же два шага, что выше, с --model .../ru_RU-irina-medium.onnx и voice_name=ru-irina
```

**Одной смены голоса мало: персона грамматически родовая.** В `soul` было «Ты ведущий…
как ведущий, который знает свою аудиторию», а `name` — «Ведущий». С женским голосом
модель продолжала бы писать «я сказал», и это слышно сразу. Поэтому вместе с голосом
правятся `name` → «Ведущая» и текст персоны, включая явную строку «о себе говори в
женском роде». Обратная смена — симметрично.

**Piper — потолок по качеству, а не по акценту.** `ru-irina` акцент снимает, но звучит
как старый синтезатор. Поскольку голос ведущего целиком задаётся эталоном, качество
поднимается сменой **источника** эталона, а не движка станции. Рабочий способ —
нейросетевой `edge-tts` (клиент читалки Edge, ключа не нужно):

```bash
python3 -m venv /tmp/tts-venv && /tmp/tts-venv/bin/pip install edge-tts   # PEP 668: в систему не ставится
/tmp/tts-venv/bin/edge-tts --voice ru-RU-SvetlanaNeural --pitch=+12Hz --rate=+6% \
  --text "<15–20 с текста>" --write-media /tmp/ref.mp3
# дальше обычная загрузка, mp3 принимается: -F 'voice_file=@/tmp/ref.mp3;type=audio/mpeg'
```

Русская женская там **одна** — `ru-RU-SvetlanaNeural`; разнообразие даёт не выбор
дикторши, а `--pitch`: выше тон — моложе голос, но заметнее обработка.

Поэтому выбор из трёх кандидатур (`a-sveta`, `b-sveta-young`, `c-sveta-younger`) был
мнимый — это был один голос с разным тоном, — и владельцу не понравилась ни одна.

Переключение между голосами — одно поле `persona.tts.voice`; при смене пола к нему
добавляется род в тексте персоны и `name`.

### Живой эталон: демо-ролики дикторов

**Планку подняла живая запись, как и предполагалось.** С 2026-09-22 эталоны берутся
из демо-роликов дикторов. Ни ролики (33 МБ чужого аудио), ни срезы в git не идут:
ролики — `<share>/radio/voices/src/`, использованные срезы (эталоны) —
`<share>/radio/voices/refs/`; `prep_voice.py` кладёт срез в `refs/` рядом с собой,
этот каталог в `.gitignore`.

**Грабля: под демо-роликом играет музыка, и Chatterbox клонирует её вместе с
голосом.** Ролик диктора — витрина, а не запись речи: подложка идёт от начала до
конца, `silencedetect` не находит тишины вовсе, громкость ровная (−8…−15 LUFS).
Пропустить её легко, а в клоне она слышна.

Чистые участки ищутся **по энергии в басу ниже 130 Гц**: женский голос там почти не
звучит, подложка звучит всегда, разница между ними около 30 dB. Делает это
[`prep_voice.py`](prep_voice.py) — находит участки, режет самый длинный (5–20 с),
грузит в библиотеку и читает им одну подводку для сравнения на слух:

```bash
python station/tts-bridge/prep_voice.py "voices/<ролик диктора>.mp3" ru-host
```

**Длина чистого куска — лотерея, и она решает больше, чем сам диктор.** Восемь
роликов дали от 1.8 до 36 с чистой речи. Chatterbox хочет 15–20 с, и нехватка видна
на секундомере: при одном и том же тексте семь проб уложились в 14–18 с, а у
`ru-voice-6` (эталон 9.1 с) вышло **25.6 с** — клон потерял темп. Сравнивать такие
пробы как «голоса» нельзя: слышна не манера диктора, а нехватка материала.

**Когда чистых кусков нет — отделять речь от музыки, а не мириться.** У ролика
`ru-voice-7` на всю длину нашлось 1.8 с. Лечится разделением:

```bash
python -m demucs --two-stems=vocals -d cpu -o <каталог> "voices/<ролик>.mp3"
python station/tts-bridge/prep_voice.py "<каталог>/htdemucs/<ролик>/vocals.wav" \
    ru-voice-7 --no-music
```

`--no-music` обязателен: **на разделённой дорожке поиск по басу не просто
бесполезен, а вреден.** Музыки там нет вовсе, поэтому «самый тихий бас» — это пауза
между фразами, и на её фоне собственный бас голоса выглядит подложкой; без флага
скрипт отвергает идеально чистый материал целиком. С флагом остаётся один критерий —
говорят или молчат.

**Прогон переживает отказы движка, потому что иначе не доходил до конца.** Пульт
вправе погасить слот посреди батча (холодный старт ~29 с), и тогда загрузка отвечает
пустотой (`curl 52`), а синтез — 502. Поэтому скрипт ждёт `/health` мостика до
работы, повторяет 5xx с паузой 15 с (мостиковых пяти не хватает: срывы идут пачками,
см. журнал находок проекта) и освобождает занятое имя перед повторной
загрузкой — `curl` без `--fail` считает успехом и ответ `voice_exists_error`, так что
иначе в библиотеке молча оставался бы старый эталон.

Состояние на 2026-09-22: в библиотеке тринадцать голосов — восемь живых дикторов
(`ru-host`, `ru-voice-4`, `ru-voice-5`, `ru-voice-7`, `ru-voice-1`,
`ru-voice-2`, `ru-voice-3`, `ru-voice-6`), клоны piper `ru-dmitri` (алиас
`alloy`) и `ru-irina`, синтетические `a-sveta`, `b-sveta-young`, `c-sveta-younger`.
Активна **`ru-host`** — голос ведущей, срез 16.5–34.5 с её ролика, прописана в
`persona.tts.voice` у `p_ru` и сверена чтением настроек обратно.

### Запасной движок обязан быть того же пола

`PIPER_VOICE` в `.env` рядом с compose — **не деталь установки, а часть образа ведущего**.
Chatterbox падает на части фраз с `502` (см. `FINDINGS.md`), станция молча откатывается на
piper, и пока тот был мужским `dmitri` при женской персоне, наружу это выглядело не
ошибкой синтеза, а **сменой пола ведущего** посреди эфира. Найти причину по эфиру нельзя:
строку «falling back to piper» контроллер пишет в лог, а слушатель слышит просто другого
человека.

```bash
cd <deploy-dir>/subwave
sudo cp -n .env .env.bak-$(date +%F)
sudo sed -i 's|ru_RU-dmitri-medium|ru_RU-irina-medium|g' .env
sudo docker compose up -d --force-recreate --no-deps controller   # сервис зовётся controller, не sub-wave-controller
```

Пересоздание безопасно: поток отдаёт отдельный контейнер `broadcast`, музыка не
прерывается, а настройки станции лежат в томе `state/` и переживают пересоздание
(проверено 2026-09-21 — персона, голос, усиление, правила дома и лимиты заказов на месте).

**Как отличить движки постфактум** — по частоте дискретизации файлов в `state/voice`:
22050 Гц у piper, 24000 Гц у Chatterbox. Это самый дешёвый способ понять, кто реально
озвучил фразу.

### Почему мостик повторяет запрос, и почему обязательно с паузой

Chatterbox отвечает `500` с ошибкой генерации на части запросов. Замер 2026-09-22 на
**одной и той же фразе** объясняет, отчего это зависит:

| Темп запросов | Отказов | Самая длинная череда подряд |
|---|---|---|
| подряд, без пауз | **20%** (3 из 15) | 3 |
| с паузой 6 с | **0%** (0 из 15) | 0 |

Дело не в тексте — гипотезы про многоточие, длинное тире и кавычки-ёлочки проверены и
**не подтвердились**: фраза, упавшая минуту назад, проходит при повторе. Дело в темпе, и
срывы идут пачками.

Отсюда устройство повтора в `bridge.py`: `RETRIES=2`, `RETRY_DELAY=5`. **Пауза здесь не
вежливость к серверу, а единственное, что делает повтор рабочим** — первая версия
повторяла мгновенно, попадала в ту же пачку и не помогала вовсе (2 из 24 фраз не
пережили трёх мгновенных попыток). С паузой — 0 падений из 24 при 15 сорвавшихся
попытках, перекрытых повтором.

Повторяются только 5xx и обрывы связи. `4xx` не повторяется: это упрёк в наш адрес,
повтором его не исправить, а слот GPU он займёт.

### Настоящая причина срывов: синтез не выдерживает двух запросов разом

Всё, что выше, лечило симптом. Корень нашёлся 2026-09-22, когда повтор перестал
справляться: **Chatterbox не потокобезопасен**. Два запроса, пришедшие одновременно,
попадают в общий батч, и падают оба — с `stack expects each tensor to be equal size`
либо `expected Tensor … got NoneType`.

Опыт, который это решает (напрямую в `:4123`, в обход повторов мостика; те же две
фразы, тот же голос, три круга):

| Как шли запросы | Успехов | Отказов |
|---|---|---|
| **одновременно, по два** | 1 | **5** |
| **подряд, с паузой 10 с** | **6** | 0 |

Опознаётся по ответам: в одном круге обе фразы упали с **одинаковыми** размерами
тензоров (`[1, 99] at entry 0 and [1, 100] at entry 2`) — то есть склеились в один
батч. «Зависимость от темпа» из замера выше — та же причина, увиденная снаружи:
запросы подряд чаще накладываются на чужой синтез, а пауза разводит их во времени.

Отсюда `MAX_CONCURRENT=1` в [`bridge.py`](bridge.py): **синтез идёт строго по одному**.
Занятый движок при этом не повод отказать — мостик ждёт очереди до `QUEUE_WAIT=60` с,
потому что на отказ станция отвечает сменой движка, и слушатель слышит чужой голос
из-за очереди длиной в один запрос. Потолок ожидания есть: контроллер всё равно ждёт
ответа не дольше 180 с (`REQUEST_TIMEOUT_MS` в `audio/remoteTts.ts`).

Проверка после правки — те же два запроса одновременно, два круга: **4 из 4 успешны**,
второй в паре приходит вдвое позже первого (8.3 с против 17.7 с), то есть действительно
отстоял очередь.

**Через мостик обязаны ходить все, включая ручные прогоны.** Очередь общая ровно
настолько, насколько общая дверь: синтез в обход, прямо в `:4123`, снова столкнётся с
эфиром в одном батче. [`prep_voice.py`](prep_voice.py) поэтому синтезирует через
`:4124/speak`, а на `:4123` ходит только за библиотекой голосов.

**Потолок этого решения.** Эталон синтетический — клонируется голос piper'а, поэтому
акцента больше нет, но тембр остаётся «как у TTS». Chatterbox клонирует с любых 10–20 с
чистой русской речи, так что качество ведущего упирается ровно в клип: живая запись
человека даст живой голос без единой правки кода. Менять движок ради этого не нужно.

## Подключение к subwave

`Admin → Settings → Voices → Default engine → Remote`, Server URL — `http://<gpu-host>:4124`
(мостик), не `:4123`. Контракт Remote — `GET /health` + `POST /speak`; Chatterbox говорит
по схеме OpenAI, мостик переводит одно в другое. Подробности — в
[`docs/deploy.md`](../docs/deploy.md).
