# subwave — эфир с ведущим

Живёт на хосте станции в `<deploy-dir>/subwave`.
Единственная часть проекта в Docker — у subwave нет нативной установки: `controller`
и `web` собираются в образы, `broadcast` — это `icecast2` + `liquidsoap` под supervisor
в одном контейнере.

## Отступление от плана: взят вариант со встроенным Caddy

План предписывал `docker-compose.byo.yml` (без Caddy), потому что на Debian уже работает
Apache. Официальная инструкция при этом требует, чтобы **перед byo-вариантом обязательно
стоял обратный прокси**: web вызывает `/api/*`, `/stream.mp3` и `/stream.opus`
**same-origin**, и эти пути вшиты в образ на build time. Без прокси страница открывается,
но плеер мёртв — ни метаданных, ни звука. Таблица маршрутов (из `docker/Caddyfile`):

```
/stream.mp3   →  host:7702      # без буферизации прокси
/stream.opus  →  host:7702
/api/*        →  host:7701/*    # префикс /api снимается
/*            →  host:7700
```

Воспроизвести это в Apache хоста значит добавить `Listen` и новый vhost в его общий
конфиг, который обслуживает и другие сайты. Правка чужого рабочего конфига ради того, чтобы не запускать
контейнер с Caddy, — плохой размен: Caddy здесь не второй edge на 80/443, а внутренний
роутер стека, слушающий один порт `:7700`. Поэтому взят дефолтный `docker-compose.yml`.

`docker-compose.byo.yml` скачан и лежит рядом на хосте: если Apache когда-нибудь станет
единой точкой входа, переключение — смена файла compose плюс блок в конфиге Apache.

**Условие наступило 2026-09-20, но переключать compose не понадобилось.** Станцию
выпустили наружу по имени (`https://<station-domain>`, см. раздел ниже), и Apache стал
внешним входом — а Caddy остался внутренним роутером стека. Apache отдаёт ему запрос
целиком и в маршрутизацию не лезет, поэтому `byo` по-прежнему не нужен: разница между
вариантами только в том, кто разбирает `/api/*` и `/stream.*`, и этот разбор
по-прежнему делает Caddy.

## Установка и восстановление с нуля

```bash
mkdir -p <deploy-dir>/subwave && cd <deploy-dir>/subwave
cp <репозиторий>/docker-compose.yml .                               # версия апстрима под форком
cp <репозиторий>/station/deploy/docker-compose.override.yml .      # наши образы, голоса Piper, комната
cp <репозиторий>/station/deploy/.env.example .env && chmod 600 .env
# заполнить .env: ADMIN_PASS, PUSH_SUBJECT и прочее — из менеджера секретов
sudo docker compose up -d
```

**`docker-compose.yml` берётся из форка, а не из `main` апстрима**, и образы апстрима
закрепляются тегом (`SUBWAVE_VERSION` в `.env`): иначе следующий `docker compose pull`
может привезти другой стек, и вернуться к работавшему состоянию будет не к чему.
Какие теги сейчас в работе:

```bash
sudo docker inspect --format '{{.Config.Image}} {{.Image}}' \
  sub-wave-controller sub-wave-web sub-wave-broadcast
```

Дальше — настройка. Либо мастер на `http://<station-host>:7700/onboarding` (вход по
`ADMIN_USER`/`ADMIN_PASS`), либо воспроизводимо, скриптом:

```bash
# переменные — из .env (см. .env.example, блок onboard.py)
set -a && . ./.env && set +a
python3 <репозиторий>/station/onboard/onboard.py
```

Скрипт делает пробы Navidrome и LLM, и **сохраняет настройки только если обе прошли**:
HTTP-код и тело ответа проверяются на каждом шаге. Тела запросов собираются
`json.dumps` — кавычка или слеш в пароле не ломают запрос (прежний shell-вариант
подставлял их в шаблон через `printf`).

TTS, персона и шоу мастером не покрываются и в скрипте не выдуманы: их снимают с
живой станции и применяют как снимок.

```bash
python3 onboard.py --export settings-snapshot.json      # секреты заменяются на ***
# подставить секреты в копию снимка и применить вместе с onboarding:
SUBWAVE_SETTINGS_FILE=settings-snapshot.json python3 onboard.py
```

Снимок с `***` скрипт применять отказывается — иначе станция получит заведомо
неверный ключ и замолчит.

### Точечные правки: `--patch` и `--persona`

Менять одну-две настройки снимком неудобно и опасно. Для этого два режима:

```bash
python3 onboard.py --patch patches/2026-09-21-voice-and-requests.json --dry-run
python3 onboard.py --patch patches/2026-09-21-voice-and-requests.json
echo '{"frequency": "chatty"}' > /tmp/freq.json
python3 onboard.py --persona p_ru --from /tmp/freq.json
```

Патчи лежат в [`patches/`](../onboard/patches/) под версионированием, а не набираются в консоли:
через месяц «почему у ведущего +6 dB» отвечается `git log`, а не памятью.

**Почему чтение обратно обязательно.** `POST /api/settings` отвечает `200` и тогда,
когда просимое не легло: незнакомый вложенный ключ контроллер отбрасывает молча, число
вне границ зажимает (`tts.gainDb` — ±12 dB), а `persona.soul` и `djHouseRules` обрезает
по 2000 символов. Поэтому `--patch` после записи перечитывает настройки и сверяет с тем,
что просили; «применено и сверено» в выводе означает именно это, а «применено» у
`--persona` — только успешный ответ на запись.

**Ловушка, на которой это чуть не сломалось.** Запись и чтение несимметричны: `POST`
принимает патч плоским (`{"llm":{"reasoning":true}}`), а `GET` возвращает те же ключи
завёрнутыми в `values` — рядом с `defaults` и `env`. Хуже того, в корне ответа лежат
**свои** `llm` и `tts`: перечень провайдеров и список движков, другие объекты с теми же
именами. Наивная сверка с корнем не просто не находит ключей, а сравнивает с чужими и
объявляет неприменённым успешно записанное; по той же причине `--persona` искал состав
персон не там и отвечал «в настройках нет массива personas». Обёртку разворачивает
`_settings_values()`.

**`personas` передаётся массивом целиком** — отправить один элемент значит стереть
остальных. Поэтому правка персоны и вынесена в отдельный режим: он читает живой состав
и заменяет в нём один элемент.

| TTS | см. ниже | |
| Выравнивание громкости | `loudness.targetLufs = -14`, `maxBoostDb = 6`, `source = replaygain-then-measured` | ReplayGain в тегах коллекции нет, поэтому работает второй источник — `library.db`. ## TTS: движка «Cloud → OpenAI-compatible» у subwave нет

Спека проекта (§5.5) предполагала подключить Chatterbox «как Cloud engine с провайдером
OpenAI-compatible». В актуальной поставке subwave такого варианта нет: Cloud — это
OpenAI и ElevenLabs по ключу, а для своего сервера есть отдельный первоклассный движок
**Remote** (`Admin → Settings → Voices → Default engine → Remote`).

Его контракт (`docs/custom-tts.md`) — два эндпоинта:

```
GET  /health  →  {"ok": true}
POST /speak   →  {"text": "...", "voice": "..."}  →  тело ответа = аудио
```

Chatterbox отвечает по схеме OpenAI (`POST /v1/audio/speech`), поэтому между ними стоит
мостик из этого репозитория — [`tts-bridge/bridge.py`](../tts-bridge/bridge.py) на
стандартной библиотеке. Server URL в админке — адрес мостика на gpu-host.

Движки запасного TTS встроены в образ контроллера, ставить их не нужно. Сайдкар
`tts-heavy` на Debian не ставим — 5–6 ГБ PyTorch при 20 ГБ свободных на `/`.

**Русскую модель Piper пришлось доложить руками** (2026-08-23): в образе лежал один
голос — `en_GB-alan-medium`, у Kokoro 54 голоса без русского, и при остановленном мостике
ведущий читал русский текст английским голосом. Каталог `/opt/piper/voices` вынесен на
хост томом ([`docker-compose.override.yml`](../deploy/docker-compose.override.yml)), в него доложен
`ru_RU-dmitri-medium`, выбор — `PIPER_VOICE` в `.env`. Деградация проверена: поток не
прерывается, ведущий продолжает говорить по-русски. Подробности — в
[`tts-bridge/README.md`](../tts-bridge/README.md).

## Встраивания: у станции их два потребителя, а настройка одна

Кроме чата у subwave есть библиотечный тэггер — kNN-разметка настроений и поиск
похожих треков. Ходит он **не** туда, куда написано в настройках LLM, а по
собственным правилам (`src/llm/internal/provider/embedding.ts`): адрес, ключ и
провайдера наследует от чата, если у блока `embedding` они пусты, а модель берёт
**дефолтом провайдера**. Для `openai-compatible` этот дефолт — `text-embedding-3-small`.

С переводом станции на шлюз (2026-09-19) это стало отказом: такой модели на шлюзе
нет вовсе, встраивания там живут под ролью `embed`, и ключу роль не выдавалась.
Каждый вызов тэггера ложился в спенд-лог как `failure` с нулём токенов — 1–3 в час
круглосуточно, и наружу это не проявлялось ничем: клиент молча обходился без
похожести. Нашлось по журналу шлюза, а не по логам станции.

Чинится с двух сторон, и обе обязательны:

```bash
# сторона шлюза: выдать ключу станции роль встраиваний (у нас — embed), значение
#   ключа не меняется
# сторона станции: имя РОЛИ вместо имени модели OpenAI
curl -u "$ADMIN_USER:$ADMIN_PASS" -X POST http://<station-host>:7700/api/settings \
  -H 'Content-Type: application/json' -d '{"embedding":{"model":"embed"}}'
```

Задаётся **только `model`**: `provider`, `baseUrl` и `apiKey` остаются пустыми
намеренно — наследование от чата и есть задуманное поведение клиента, поэтому
ротация ключа шлюза правится в одном месте, а не в двух. Проверка до сохранения —
`POST /api/settings/embedding/probe` с тем же телом: отвечает `{"ok":true,"dim":1024}`
(1024 — bge-m3; размерность клиент определяет пробой живого сервера, поэтому
произвольное имя роли вместо имени модели ему не мешает).

**Разметка сделана 2026-09-22** — до неё в `/api/doctor` стояло `mood-tag coverage:
no tracks tagged yet` и `embedding.seedCount = 0`, а половина источников пула молчала
(`mood-library`, `embedding-similar`, `mood-wildcard`). Запуск — `POST /api/tag-library`
с явными шагами; поле, не переданное в теле, означает «фазу выполнить», а не «пропустить»:

```bash
curl -su "$ADMIN_USER:$ADMIN_PASS" -X POST http://127.0.0.1:7700/api/tag-library \
  -H 'Content-Type: application/json' \
  -d '{"reconcile":false,"enrich":false,"tagMoods":true,"analyze":false,"vocal":false}'
```

**Страшилка про слот GPU оказалась неверной.** Здесь раньше стояло, что прогон 4631
трека «берёт слот GPU на gpu-host и вытесняет прод-OCR». На деле встраивания идут в
`bge-m3` на `<gpu-host>:30000` — отдельный постоянный сервис, не через `slot-gate`;
проба отвечает за 0.2 с, а вся фаза `embed` на 4631 трек заняла **5 минут** (батчи по
50, ~93 запроса). Дорога не она, а разметка настроений — см. ниже.

**Пайплайн тэггера и где он спотыкается** (`src/music/tag-library.ts`):

| Фаза | Что делает | Как прошла |
|---|---|---|
| 0 ENRICH | Last.fm, лирика, год сборников через MusicBrainz | 4631 за 100 с; Last.fm **0** (ключа нет), лирика 103. MusicBrainz тогда был **недоступен** (с 23.09 ходит через VPN) — фаза висела на таймаутах; повторно гонять с `enrich: false` |
| 1 EMBED | вектор на каждый трек | 4631 за 5 минут |
| 2 SEED | LLM размечает опорную выборку | 200 треков (70 стратифицированных + 130 k-means) |
| 3 PROPAGATE | kNN разносит метки на остальных | **0 треков** — см. ниже |
| 4 ACTIVE-LEARN | LLM добирает всё неуверенное | 4606 треков, ~1.4 с на трек |

**Propagate на этой библиотеке не работает, и это не сбой.** 200 размеченных на 4631 —
4%; при `knnK = 10` у нетегированного трека в десятке соседей размеченного обычно нет
вовсе, голосовать нечем, и все 4606 уходят в `learn`. То есть цена разметки — не 8
батчей, как кажется по `batchSize: 25`, а **4606 обращений к модели**: она отвечает не
пакетом, а по треку («didn't return one entry per track — tagging individually»).
Порядка полутора часов и ~0.5–1 млн токенов роли `chat`.

**Размерность векторов рассогласовывается с контроллером, и это роняет прогон.**
Таблица `track_vectors` была заведена под 768, `bge-m3` даёт 1024; тэггер пересоздал
её («recreating at 1024-d»), а живой контроллер держал в памяти прежнее значение — на
переходе `embed → seed` стек перезапустился и убил разметку. После рестарта в логе
`adopting on-disk embedding dim 1024`, и повторный прогон проходит спокойно. Вывод:
первый прогон после смены модели встраиваний **закладывать на один перезапуск**, а сам
прогон перезапускать — он продолжает с уже записанного (метки пишутся по ходу).

Не путать с самим `library.db`: с 2026-09-20 в нём лежат метаданные всех 4631
трека (сверка с Navidrome, см. раздел про экран блокировки).

## Размышление модели уезжало в эфир: `llm.reasoning` включается, а не выключается

За ролью `chat` стоит `glm-5.3-flash` — модель **thinking-only**, размышление у неё
не отключается в принципе (шлюз это знает: `thinking: disabled` отвергается upstream'ом
с [1210] «This model always engages in thinking»). Пока `llm.reasoning` был выключен,
клиент на каждый запрос подмешивал в тело набор подавителей — `enable_thinking: false`,
`reasoning_format: 'deepseek'`, `thinking: {type:'disabled'}`, `reasoning: {enabled:false}`
(`src/llm/internal/provider/registry.ts::openAICompatibleFetch`, ветка `noThink`).
Отключить размышление они не могут, но **ломают разделение полей**: провайдер перестаёт
класть его в `reasoning_content` и сваливает всё в `content` — без `<think>`-тегов,
поэтому `stripThinking()` в контроллере их не находит.

Замер на живом шлюзе (2026-09-20), один и тот же промпт подводки:

| Запрос | `content` | `reasoning_content` |
|---|---|---|
| без подавителей | 184 символа, чистая реплика | 102 символа |
| с подавителями клиента | **2804 символа** размышления вслух + ответ в хвосте | пусто |

Отсюда `502 string_too_long (at most 3000 characters)` от мостика и молчаливый откат
на piper, а в лог `[link]` писалась та же простыня — по логу казалось, что модель
сошла с ума, хотя реплика в её хвосте была короткой и правильной.

Лечится одной настройкой, и она **контринтуитивна**: размышление надо **разрешить**.

```bash
curl -u "$ADMIN_USER:$ADMIN_PASS" -X POST http://<station-host>:7700/api/settings \
  -H 'Content-Type: application/json' -d '{"llm":{"reasoning":true}}'
```

Тогда подавители не подмешиваются вовсе, шлюз отдаёт поля раздельно, AI SDK забирает
в `result.text` только ответ, а размышление остаётся в своём канале. Проверка — по
живому эфиру: `[link]` содержит реплику, а не рассуждение, и в логе нет `remote failed`.

**Следствие: агент-пикер стал медленнее** — размышление теперь идёт честно, и в
прежние 45 с он перестал укладываться (`djAgentPick agent run exceeded 45000ms
deadline — falling back to pool`). Дедлайн поднят до 90 с
(`{"llm":{"agentTimeoutMs":90000}}`); в `/api/doctor` это видно как
`agent deadline · 90s before falling back to the pool`.

## Чат: комната снаружи, навык внутри

Слушатели пишут в комнату из плеера (пятый ящик, клавиша `5`), ведущий читает
новое навыком `chat` и отвечает голосом в эфире. Устройство комнаты, её
поверхность и проверка — [`room/README.md`](../room/README.md); здесь
только то, что касается станции.

**Операторский навык приходит выключенным.** Положить каталог в
`state/skills/<slug>/` мало: `GET /api/dj/skills` покажет его с
`enabled: false`, и это гейт ревью апстрима («dropping a folder never auto-airs
unreviewed content/code»), а не сбой установки. Включается в админке либо
`POST /api/dj/skill-toggle` с телом `{"name":"chat","on":true}` — поля
называются `name` и `on`, не `skill`/`enabled`.

**Ручной запуск навыка не проверяет молчание.** `POST /api/dj/skill`
(тело `{"name":"chat"}`) — явная команда оператора, и апстрим намеренно
выполняет ровно то, что названо, минуя гейты. Поэтому на пустом чате ведущий
в таком запуске всё равно скажет реплику — сочинит по брифу. Молчание живёт в
автономном пути, где агент сам решает `air: false`. Проверять «молчит ли он,
когда писать некому» ручным запуском бесполезно.

**Повторно прочитанное не зачитывается.** Навык помечает каждое сообщение через
`services.recall` — долговременный журнал, переживающий рестарт контроллера.
Курсор `state.chatSince` — только быстрый путь внутри процесса.

## Отказы ведущего: фильтра в subwave нет, правила дома были пусты

Собственного фильтра лексики у subwave нет ни одного — всё, что выглядит как цензура,
приходит от модели. Рычагов на неё два, и оба текстовые: `persona.soul` и
`settings.djHouseRules`. На 2026-09-21 второй был **пуст (0 символов)** — то есть
станция не сообщала модели ровным счётом ничего о том, кто её слушает, и та
осторожничала по умолчанию, как в публичном эфире.

Правила дома заведены под версионированием —
[`patches/2026-09-21-house-rules.json`](../onboard/patches/2026-09-21-house-rules.json), 1042 символа
при пределе 2000: аудитория — взрослые у себя дома, объявление песни не есть её
одобрение, тяжёлую тему называть спокойно и без предостережений.

**Чего это не делает и обещать нельзя.** Выравнивание провайдера текстом не отключается.
Правила снижают осторожность, но там, где стоит настоящий запрет, отказ останется — и
в самих правилах прямо сказано отказываться молча, коротким объявлением трека, а не
объяснением, почему не можешь: разница между «модель отказала» и «ведущий прочитал
вслух дисклеймер» слышна в эфире, вторая хуже.

**Замер после правил: отказов нет.** Шесть подводок подряд через
`POST /api/dj/segment` с телом `{"type":"link"}` — **6 из 6 успешны, 0 отказов**,
15.7–23.7 с на генерацию. Тексты в персоне: спокойные, без тона коммерческой FM.

Поле называется **`type`, а не `kind`** (план ошибался), и допустимых значений семь:
`station-id`, `hourly`, `link`, `banter`, `programme-intro`, `programme-feature`,
`programme-outro`. Неверное значение отвечает `400` со списком — endpoint сам себя
документирует.

**Чего этот замер не доказывает.** Числа «до» не существует: правила дома были применены
раньше, чем появилось разрешение дёргать генерацию, так что сравнивать не с чем. И шесть
подводок пришлись на один и тот же трек (`Depeche Mode — It's No Good`) — материал, на
котором отказу взяться неоткуда. Отказы, если они есть, ждать надо на треках с
откровенными названиями и темами, а такой выборки здесь не было.

**Побочное наблюдение.** В одной реплике из шести текст поехал синтаксически:
«Сорок третьего года городу, в котором я жил, было двадцать два тридцать два». Похоже на
попытку выговорить время; на отказ не похоже, но в эфир такое уходит как есть.

**Развилка плана закрыта не так, как он предполагал.** План допускал, что отказы идут
от роли, которой станции не выдали. Роль `chat` выдаётся и обслужила 3002 вызова с
одной ошибкой (`/api/doctor`), так что чинить в шлюзе нечего — дело только в тексте.

## Эфир при нуле слушателей: `pauseWhenEmpty`

Станция крутила LLM круглосуточно независимо от того, слушает ли её кто-нибудь:
~44 вызова в час (выбор трека + подводка на каждый трек), около трети месячного окна
подписки OCG. У контроллера для этого есть готовый гейт — `llm.pauseWhenEmpty`:

```bash
curl -u "$ADMIN_USER:$ADMIN_PASS" -X POST http://<station-host>:7700/api/settings \
  -H 'Content-Type: application/json' -d '{"llm":{"pauseWhenEmpty":true}}'
```

`broadcast/listeners.ts::djCallsAllowed` гасит **автономные** вызовы ведущего, когда
Icecast насчитал ноль слушателей, и **fail-open по неизвестности**: если статистика
Icecast недоступна, счёт считается занятым и ведущий продолжает работать — сбой сбора
метрик не может увести станцию в тишину. Заказы слушателей (`POST /request`) гейт
пропускает всегда, музыка идёт всегда — глохнет только LLM.

## Станция наружу: `https://<station-domain>`, она же устанавливаемое приложение

Плеер subwave — **готовое PWA из апстрима**: `/manifest.webmanifest` (display
`standalone`, четыре иконки, включая maskable, два скриншота) и свой `/sw.js` с
разумной стратегией кэша — поток и `/api/*` в обход, `_next/static` cache-first,
HTML network-first. Писать ничего этого не пришлось.

Не устанавливалось оно по одной причине: service worker требует защищённого
контекста, а станция жила на `http://<station-host>:7700`. Включатель — домен и TLS,
всё остальное уже было на месте.

Конфиг: [`apache-fm.conf.example`](../deploy/apache-fm.conf.example) +
[`robots-fm.txt`](../deploy/robots-fm.txt); подключается одной строкой
`IncludeOptional` в конфиг Apache хоста (бэкап файла — перед правкой, после —
`apache2ctl configtest`, `graceful` и удаление бэкапа). Два виртуальных хоста: `*:80` редиректит на https,
`*:<https-port>` терминирует TLS и проксирует всё на `127.0.0.1:7700`. Конкретика
установки (DNS, сертификат, NAT) ведётся вне репозитория.

**`SITE_URL` в `.env` переведён на новый адрес.** Из него строятся абсолютные адреса,
OG-теги и sitemap; пока там стоял `http://<station-host>:7700`, `og:image` уезжал на
внутренний адрес по http. Переменная читается в рантайме, пересборка образа ради неё
не нужна — достаточно `docker compose up -d web`.

**Что закрыто от интернета.** Станция открыта всем, кто знает адрес (осознанное
решение), но правящие её пути ограничены приватными сетями:
`/admin`, `/api/settings`, `/api/system`, `/api/debug`, `/api/doctor`, `/api/backup`,
`/api/mcp`. У контроллера поверх этого свой `requireAdmin`, это второй рубеж:
пароль один, лежит в `.env`, и через `/api/settings` им меняются ключ шлюза LLM и
адрес Navidrome. `/api/onboarding` в список **не входит намеренно** —
`/api/onboarding/status` отвечает 200 без пароля, по нему web решает, показывать ли
мастер, и закрытый префикс сломал бы публичную страницу.

Проверено подменой списка разрешённых сетей на заведомо чужой: перечисленные пути
отдают 403, а `/`, `/manifest.webmanifest` и `/api/onboarding/status` — 200. Из дома
запрос по этому же имени приходит с <router> (петля на роутере) и проходит; прямой
вход `http://<station-host>:7700/admin` от правила не зависит вовсе.

**Роботы заблокированы.** Апстримный `/robots.txt` отдаёт `Allow: /`; на публичном
домене он подменяется своим с `Disallow: /`, плюс заголовок `X-Robots-Tag: noindex`.
Причина не в скрытности, а в счётчике: краулер засчитывается Icecast как слушатель,
снимает гейт `llm.pauseWhenEmpty` и жжёт окно подписки круглосуточно без единого
живого слушателя.

**Все внешние слушатели приходят в Icecast одним адресом.** Caddy перезаписывает
`X-Forwarded-*` для пиров вне своего `trusted_proxies` (там только сети Cloudflare), а
Apache туда не входит. Следствие — таблица Listeners и per-IP лимиты контроллера
считают всех за одного. Лечится доверием к адресу Apache в Caddyfile, но у этого свой
риск: `:7700` открыт в LAN, и оттуда заголовок можно подделать. Оставлено как есть.

### Как установить и почему браузер сам не предлагает

Критерии установки проверены и выполнены: HTTPS, манифест с `display: standalone`,
иконки 192 и 512 (обычные и maskable) — настоящие PNG ровно заявленных размеров,
скриншоты 1280×720 и 720×1280, service worker с обработчиком `fetch`. Проверено не
по коду ответа, а по поведению: на чистом профиле браузера worker регистрируется с
первой загрузки и заводит свой кэш `subwave-shell-v2`.

**Предложения всё равно не было, и причин оказалось две.**

**Первая — настоящая поломка: Chrome не видел манифест.** Он ищет
`<link rel="manifest">` только в `<head>`, а страница плеера `force-dynamic`, и
Next стримит весь блок Metadata API в **тело** документа (`</head>` кончался на
байте 7186, ссылка Next лежала на 41881). Сам Chromium это и сказал —
`Page.getInstallabilityErrors` отвечал `no-manifest` при живой ссылке в DOM и
`200` на `fetch`. Safari читает такие теги и из тела, поэтому на iPhone станция
ставилась и поломка ничем себя не выдавала. Чинится строкой в `<head>` — тем же
приёмом, которым апстрим уже спасал `og:image`. После правки тот же прогон даёт
`installabilityErrors: []`, как у эталонных PWA.

**Вторая — поведение браузера.** Мини-инфобар Chrome убрал: `beforeinstallprompt`
приходит, но сам по себе не показывает ничего, предложение обязан вывести сайт.
У апстрима такого кода нет вовсе. С 2026-09-20 он есть у нас: в шапке плеера
кнопка со стрелкой вниз, она переигрывает перехваченное событие. Разбор обоих
пунктов — в [`web-changes.md`](web-changes.md).

**Проверять установимость — самим браузером, а не глазами по критериям.** Список
критериев сходился и при неработающей установке. Авторитетный ответ даёт Chromium:
DevTools → Application → Manifest, либо headless по CDP (`Page.getAppManifest` +
`Page.getInstallabilityErrors`), обязательно с контролем на заведомо
устанавливаемом стороннем PWA — иначе не отличить поломку станции от особенностей
headless.

| Где | Что происходит |
|---|---|
| **Chrome, Edge (десктоп и Android)** | Кнопка в шапке плеера. Дублируется значком установки в адресной строке (десктоп) и пунктом меню ⋮ |
| **iPhone, iPad** | Системного предложения не бывает **никогда** — Safari не поддерживает `beforeinstallprompt`. Кнопка в шапке есть, но она лишь подсказывает маршрут: «Поделиться» → «На экран „Домой“» |
| **Уже установлено** | Кнопка не показывается вовсе (проверка по `display-mode` и `navigator.standalone`), у браузера вместо предложения — «Открыть в приложении» |

**Установленное приложение не переименовывается само.** iOS запоминает подпись и
иконку в момент добавления на экран, поэтому после смены имени или знака ярлык надо
удалить и добавить заново.

### Экран блокировки телефона

Три вещи, которые до 2026-09-20 не работали и чинятся только на стороне `web`
(разбор — в [`web-changes.md`](web-changes.md)):

| Что | Причина | Чем чинится |
|---|---|---|
| Прогресс трека | У живого потока `audio.duration` = ∞, а `currentTime` считает соединение | Явная публикация `mediaSession.setPositionState` из `/now-playing` + `trackStartedAt` |
| Смена песни | Блокировка экрана на iOS — это `document.hidden`, а опрос станции целиком вставал | Опрос при включённом эфире продолжается в фоне, раз в 15 с |
| Выключение звука | Апстрим выключал звук через «громкость 0», а на iOS `volume` только для чтения | Нулевая громкость зеркалится в `el.muted`, который iOS слушает |

Полоса прогресса там **только для чтения** — поток не перематывается, обработчики
`seekto` намеренно пустые. Регулятора **уровня** на iOS нет и быть не может.

**Прогресс требует, чтобы станция знала длительность трека.** Её нет в метаданных
Liquidsoap: контроллер берёт её из очереди (заказы и выбор ведущего) либо из
`library.db`. Пока индекс был пуст, треки автоплейлиста (`source: auto`) шли без
длительности — и у них молча пропадали и полоса в плеере, и часы, и прогресс на
экране блокировки. Наполняется дешёвой сверкой, без LLM и GPU:

```bash
curl -u "$ADMIN_USER:$ADMIN_PASS" -X POST http://<station-host>:7700/api/library/reconcile -d '{}'
```

Это `Admin → Library → Reconcile with Navidrome`: обход каталога с записью
`title/artist/album/year/genres/duration` в `library.db` и удалением строк, которых
в Navidrome больше нет. 4631 трек — секунды. Разметку настроений она **не**
запускает (`mood-tag coverage` остаётся `no tracks tagged yet`), это отдельное
решение. Побочный эффект, он же бонус: в метаданных плеера появился жанр из тегов
коллекции — у двух файлов из 4631 он записан в cp1251 и читается кракозябрами
(`Äðóãîå`, `Ðîê`); это данные коллекции, а не сбой станции.

`Icy-Url` в метаданных потока остался `http://localhost:7700` — его подхватывает
контейнер `broadcast`, а он при этой работе не пересоздавался. Значение косметическое
(его показывают внешние плееры вроде VLC), а пересоздание рвёт эфир, поэтому отложено
до ближайшего планового рестарта стека.

## Заметки по настройке

Состояние конкретной установки ведётся вне репозитория.

Первичная настройка выполнена скриптом [`onboard.py`](../onboard/onboard.py) (до 2026-09-17 —
`onboard.sh`, заменён: shell не экранировал секреты и не смотрел на HTTP-код),
персона и TTS — через тот же API. **Кириллицу отправлять только телом из файла или
из Python**: `curl -d "…"` из Git Bash приводит русский текст к `?????` — так уехало
название шоу с первой попытки.

**Интерфейс плеера переведён своим образом `web`** (2026-09-20). i18n у subwave нет
вовсе — ни каталога переводов, ни языковой настройки: `locale` принимает только
`en-GB`/`en-US` и управляет форматом времени, а строки лежат прямо в компонентах.
Поэтому `web` собирается из форка — апстримный тег и наши коммиты поверх, остальные
контейнеры остаются апстримными; порядок сборки, что переведено и что намеренно нет —
в [`web-changes.md`](web-changes.md).
Английскими остаются названия треков и исполнителей, имена клавиш и теги коллекции.
Админка (`/admin`) не переводилась — ей пользуется один человек и только при настройке.

### Брандмауэр хоста

Если у хоста `INPUT policy DROP`, контроллеру в контейнере нужно узкое правило на порт
Navidrome из подсети стека (`docker network inspect <сеть стека>`), иначе проба в
мастере молча падает по таймауту. Правило конкретной установки ведётся вне репозитория.
