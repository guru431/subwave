# Изменения форка в контроллере станции

Что форк меняет в `controller/` апстрима, зачем и чем это проверено. Каждая фича —
отдельный коммит `feat|fix(controller): …` поверх тега апстрима на `main`
(`git log --format='%h %s' v1.17.0..main -- controller`); разделы ниже идут в порядке
коммитов, заголовок раздела — заголовок коммита. Код фичи в таблице переноса
(`C01`–`C13`) стоит первой строкой раздела: история переноса с v1.8.0 на v1.17.0,
конфликты и вердикты — [port-1.17.md](port-1.17.md). Описан код **как он есть на
`main`**; как было в патче v1.8 — только там, где это объясняет решение.

Изменения веба (`web/`) — в [web-changes.md](web-changes.md). Собирается всё это в
свой образ `subwave-controller:1.17.0-ru` (раздел [«Сборка»](#сборка)).

## Заказ встаёт перед несданными авто-пиками

`C01` · [queue.ts](../../controller/src/broadcast/queue.ts), `Queue.push()`;
[dj-agent/enqueue.ts](../../controller/src/broadcast/dj-agent/enqueue.ts) `enqueuePick` —
момент правил пика (ниже, «Пик, сдвинутый в чужое шоу»)

Апстрим кладёт заказ слушателя **в хвост** `upcoming`. При глубокой очереди
([`queue.lookahead`](#глубина-очереди-queuelookahead)) заказ ждал бы всю пачку
авто-пиков, а заказчику нужно, чтобы он играл сразу после текущего трека. Очередь
ведёт сам контроллер, снаружи это не настраивается.

Заказ (`!aiPicked && requestedBy`) вставляется **перед первым несданным
авто-пиком** (`!sent && aiPicked`):

- `sent` (отданное в Liquidsoap) не трогается **никогда** — перебивать играющее и
  уже переданное нельзя;
- заказы, уже стоящие в очереди, остаются впереди: очередь заказов честная (первым
  пришёл — первым сыграл). Блок студии (#1622, `requestedBy: 'studio'`) встаёт так
  же, члены блока — в своём порядке: каждый следующий вставляется перед тем же
  первым несданным авто-пиком;
- `push()` возвращает позицию **этого** элемента (с единицы), а не длину очереди:
  вызывающие сообщают её слушателю («вы номер N»), а после вставки хвост — уже
  чужой. Строка журнала `queued` несёт ту же `position`. Маршрут заказа берёт
  `queuePosition` из этого возврата на всех четырёх путях: точный заказ (C02), «more
  like this», агент заказа (`runRequest` отдаёт `queuePosition` вместе с ответом) и
  каскад без агента. `queue.upcoming.length` там больше нет — при глубине 5
  слушатель видел «#6» вместо «#1».

Под признак заказа попадает и ручная постановка из студии: поставить трек руками
значит хотеть его скоро, а не через десять песен.

**Пару перехода заказ не разрывает** (`requestInsertIndex`, исправлено по финальному
ревью переноса). Первый несданный авто-пик может быть уже **в паре** с тем, что
играет перед ним: стем-шов (его начало вмешано в клип впереди) или, при парном
сливе апстрима (`pairDrainActive()` — персона с djMode, `transitions.pairDrain`),
преемник, под которого отправлен предыдущий трек — или трек в эфире, если пик стоит
головой. Вставка между ними пустила бы переход в чужую песню, поэтому заказ встаёт
на слот дальше — перед следующим несданным авто-пиком, а нет такого — в хвост. Без
пары — как прежде. Та же проверка (`pairedWithPredecessor`) бережёт пару и при
снятии устаревших пиков (ниже).

**Голова, которую слив уже отдаёт, — отданная.** Слив берёт голову через
`find(i => !i.sent)` и ставит ей `sent` только после громкости, беда и
`writeHandoff` — до секунды на стык. Заказ или член блока студии, пришедший в это
окно, `requestInsertIndex()` ставил перед головой (без djMode пары нет): голова
уходила в Liquidsoap, заказ оставался несданным впереди неё, `DRAIN_AHEAD` его не
пропускал, а `onTrackStarted` срезом `splice(0, idx + 1)` выбрасывал его как
«Dropped … during the downtime» — слушателю при этом ответили «позиция 1». Теперь
элемент, захваченный сливом (`Queue._drainingItem`: ставится до первого `await`,
снимается вместе с `sent` и в `finally`), для вставки считается отданным, а
`onTrackStarted` срезает перед совпадением только `sent`-элементы — несданное
Liquidsoap не получал и сыграть не мог. Метка — поле очереди, а не элемента: в
`queue.json` она не попадает, и контроллер, упавший посреди слива, не оставит её
залипшей.

**Подводки это не ломает — по устройству апстрима.** `airIntro` сверяет `linkPrev`
и снимает back-announce, если вклинившийся заказ сделал фразу «а это была X»
неправдой. Комментарий к `push()` в апстриме описывает ровно этот сценарий (#189):
вклинивание заказа там предусмотрено, просто не сделано.

**Проверено.** `scripts/request-position.test.ts` — заказ за пятью несданными
авто-пиками встаёт первым и получает `queuePosition: 1` на трёх ветках: «more like
this», каскад без агента и агент заказа (модель подделана по форме запроса:
`searchLibrary`, затем `done`). RED → GREEN: каскад с длиной очереди — 6, агент без
`queuePosition` в возврате `runRequest` — `null`. `scripts/queue-request-pair.test.ts` —
пара перехода: заказ ждёт за преемником отданного трека и за головой при треке в
эфире, стем-шов не разрывается и без парного слива, единственный преемник — заказ в
хвост (RED → GREEN); контроль — без пары заказ встаёт перед первым несданным.
`scripts/queue-request-drain-race.test.ts`
— настоящий слив, остановленный между захватом головы и `sent`: заказ, пришедший в
это окно, встаёт за головой (позиция 2) и переживает её выход в эфир; старт трека
срезает впереди только отданное (RED → GREEN: заказ впереди отданной головы, после
её старта очередь без заказа). При переносе — `run-tests.sh --src`, наборы `queue*`, `request*`,
`pair-drain-interleaving` (125/125): у апстрима v1.15 появился слив парами (#1652),
и вставка проверялась вместе с ним.

### Пик, сдвинутый в чужое шоу, снимается

Добор ([C03](#добор-очереди)) останавливается у границы шоу только для **новых**
пиков. Заказ или блок студии встаёт перед несданными авто-пиками — обгон
намеренный — и сдвигает их позже, а их никто не перепроверял. Длинный блок
незадолго до смены шоу переносил до `lookahead − 1` пиков уходящего шоу в
следующее: после передачи микрофона между приветствием нового ведущего и его первым
треком звучали треки старого. Решение владельца — **снимать устаревший пик**:

- авто-пик помнит шоу, по правилам которого выбран: `pickedForShow` — ключ
  `show-boundary.showKeyAt` (`show:<id>` или `default`) в момент `showAt` цикла пика
  (пустой `showAt` — «сейчас», как читает его `pickViaAgent`). Момент доходит до
  `push()` из обоих путей пика через `enqueuePick` (`showAt`), штамп ставит очередь;
- несданный авто-пик снимается, если он выбран для шоу, которое в эфире **сейчас**, а
  прогноз его эфира (`airForecastSec` — тот же, что у предупреждения блока
  `runsPastShowChange`, плюс `PICK_SHOW_LOOKAHEAD_SEC`, как у самого пика) попал в
  другое шоу — чистая `pickOutlivedShow` в `queue/pure.ts`. Пик, выбранный на
  **следующее** шоу, не снимается: назад через границу его двигают только пропуск и
  отмена, ранний выход заглядывающего пика задуман апстримом и учтён передачей
  микрофона, а снятие поставило бы после передачи пик уходящего шоу;
- не трогаются никогда: заказы и члены блока (они не авто-пики), отданное и
  захваченное сливом, пик в паре с тем, что играет перед ним (стем-шов, пара
  `pairDrain` — та же `pairedWithPredecessor`, что у вставки заказа), **финальный
  трек** взведённой передачи микрофона (`session.boundaryHandoffReadyForTrack`: на нём
  ждут прощание и приветствие —
  [show-boundary-handoffs.md](../../docs/internals/show-boundary-handoffs.md)), пик без
  штампа (`queue.json` до правки) и пик без прогноза (часы неизвестны);
- снятие видно в будке: строка `scheduler` «Dropped N auto-pick(s) chosen for "<шоу>"
  — what was queued ahead now carries them into <шоу>: …» с названиями треков. Замену
  тут же никто не выбирает: треки нового шоу даёт обычный добор или пик на пустой
  очереди, по правилам нового шоу.

**Где перепроверка.** Сразу после вставки заказа или члена блока в `push()` —
синхронно, до `persist` и пинка слива, так что слив не успеет отдать устаревший
пик, а позиция вставленного элемента не меняется (сниматься может только то, что за
ним). И в `finally` цикла пика, если за время цикла был такой push (`Queue._jumpSeq`):
пик, который модель выбирала, пока вставлялся блок, ложится уже за блоком, а
проверка в `push()` прошла до его появления. Снятие идёт до подсчёта `grew`, поэтому
снятый пик не запускает следующий добор. Других причин сдвинуть несданный пик
**позже** у очереди нет: пики добавляются в хвост, отмена и пропуск двигают раньше.

Не перед сливом головы: снятие там съело бы запас времени у замены (при `pairDrain`
голова сливается за ~120 с до конца трека), а мелкий дрейф — бед, обрезка тишины —
и есть то, что поглощает запас `PICK_SHOW_LOOKAHEAD_SEC` самого пика. И не при
каждом push самого пика: его прогноз отличается от оценки цикла на скрытые паузы
(бед, тишина паузы-и-разговора), и у границы пик снимался бы сразу после выбора —
по вызову модели на каждом стыке.

**Несданный элемент впереди прогноз считает так, как его отрежет слив**
(`Queue.undrainedPlayableSec`, исправлено по ревью пачки). `cueOutSec`/`cueInSec`
ставятся элементу только на его сливе, и `airForecastSec` считал несданные пики
впереди целиком: пик с длиной 900 с при `maxTrackSeconds` 200 сдвигал прогноз на
11 минут, и `dropStalePicks` снимал пик, который уложился бы в своё шоу, — лишний
вызов модели на замену. Теперь для несданного элемента берётся та же композиция,
что у слива для `resolveBoundaryCut`: потолок длины `settings.effectiveMaxTrackSec()`
(у заказа — нет) и обрезка тишины `silenceTrim.resolveSilenceTrim`, раньший конец
выигрывает, отсчёт от обрезанной головы (`playableDurationSec`). Отрезка у границы
шоу и стем-шов не учитываются: их решает слив по этому же прогнозу. Тот же прогноз
читают фраза ожидания заказа и предупреждение блока `runsPastShowChange`: для них
это тоже точнее и только короче, у заказов впереди — лишь на обрезанную тишину.
Проверено в `scripts/queue-stale-pick.test.ts`: несданный пик впереди с потолком
длины и с 30 с тишины в хвосте не сталкивает следующий за ним пик в чужое шоу
(RED → GREEN: пик снимался).

Чего правка не делает: блок по-прежнему встаёт вперёд и играет сразу, а передача
микрофона при блоке через границу ведёт себя как прежде — её выпускает цикл пика
(раздел блока в [`docs/internals/broadcast.md`](../../docs/internals/broadcast.md)).

**Проверено.** `scripts/queue-stale-pick.test.ts` — граница шоу задана временным
переключением (как в `show-boundary-drain.test.ts`): блок перед сменой шоу снимает
сдвинутый пик, заказ, члены блока, отданное и пик без штампа целы, строка будки
называет трек и шоу; сдвиг внутри своего шоу и пик, выбранный на следующее шоу, не
снимаются; финальный трек взведённой передачи остаётся; пик, который выбирался, пока
вставлялся блок, снимается в `finally` настоящего `runPickCycle` (подделаны только
модель и погода); штамп `pickedForShow` у пика и его отсутствие у заказа. RED →
GREEN: сдвинутый пик оставался в очереди, штампа не было; без проверки шоу «в эфире»
снимался пик следующего шоу, без защиты финального трека — сам финальный трек, без
перепроверки в `finally` — пик, выбранный во время вставки.

## Точный заказ по songId

`C02` · [schemas/request.ts](../../controller/src/schemas/request.ts),
[routes/request.ts](../../controller/src/routes/request.ts)

`POST /request` принимал только свободный текст, который разбирал LLM-каскад; поля с
идентификатором трека не было, а публичного поиска по библиотеке у контроллера нет
вовсе — `GET /dj/search` и весь `/library/*` под `requireAdmin`. Поэтому сверка с
коллекцией живёт в [комнате](../room/README.md), а контроллеру остаётся принять её
результат.

- `schemas/request.ts` — необязательное поле `songId`: строка, `trim`, до 64
  символов. Потолок не потому, что id Navidrome бывают длиннее, а потому, что
  значение уходит в запрос Subsonic. Файл **копируется в бандл плеера и может
  импортировать только `zod`** — это проверяют линтер и генератор зеркала; само
  зеркало `web/lib/schemas.generated.ts` **генерируется**, а не правится руками
  ([«Линтер и зеркало схем»](#линтер-и-зеркало-схем--на-рабочей-машине)). Плеерная
  сторона — W09 в [web-changes.md](web-changes.md).
- `routes/request.ts` — запись заказа несёт `songId` (пустая строка — «не
  выбирали», то есть `null`), и ветка `0a` в `resolveRequest`, перед «more like
  this»: трек берётся `subsonic.getSong(id)`, весь каскад (поиск, разбор намерения,
  выбор из кандидатов) пропускается; `pickSource` — `song-id`.

**Подводка при этом остаётся.** Экономится сопоставление, а не голос: заказ,
объявленный по имени слушателя, — то, ради чего станция и заводилась. Ветка идёт
общим путём подводки заказа v1.17 — `generateQueuedRequestIntro`: выключенный голос
станции означает ни подводки, ни вызова модели, а ответ слушатель получает всё
равно; эхо текста заказа в подводке ловит тот же сторож (`request-guard` в журнале).

Отказы — те же, что у каскада, и ничего не выдают:

| Случай | Ответ |
|---|---|
| по id трека нет (коллекция переиндексирована, чужой id) | `sorryNoMatch`, в журнале `song-id … не найден в коллекции` |
| трек звучал внутри `requests.repeatCooldownMin` | `cooldownAck`, `pickSource` — `song-id:cooldown`, `queuePosition: null` |
| трек под блокировкой (`push()` → `-2`) | тот же `sorryNoMatch`, `pickSource` — `song-id:blocked` |
| трек уже в очереди (`push()` → `-1`) | `dedupAck`, `queuePosition: null` |

**Пауза повтора — та же, что у каскада** (исправлено по финальному ревью переноса).
Ветка `0a` пропускала каскад вместе с проверкой `requests.repeatCooldownMin`, и на
станции с `onePendingPerIp: false` слушатель мог заказывать одну песню каждый раз,
как она отзвучит: точность выбора не даёт такого права. Проверка —
`queue.recentlyPlayedIds(cdMin / 60)`, как в каскаде, и стоит **до** подводки: отказ
не стоит вызова модели.

`queuePosition` берётся из возврата `push()`: заказ встаёт перед несданными
авто-пиками, и хвост очереди — уже чужой. Ответ — текст подводки либо «В очереди:
«…» — …», через `withWaitNotice` (фраза ожидания при длинной очереди — в
[«Готовые ответы на заказ по-русски»](#готовые-ответы-на-заказ-по-русски)).

Апстримный `scripts/request-host-speech.test.ts` считает вызовы общего шва подводки
в маршруте; наша ветка — третий каскад, число поправлено с 2 на 3.

**Проверено.** `scripts/request-song-id-cooldown.test.ts` — настоящий роутер по HTTP
(подменены Navidrome, Icecast и модель): точный заказ недавно звучавшей песни
получает отказ паузы повтора, контроль — свежая песня встаёт в очередь (RED → GREEN).
При переносе — `run-tests.sh --src`, `request*` и `*schema*` (373/373, одно падение
из `KNOWN`).

## Глубина очереди queue.lookahead

`C03` · [queue.ts](../../controller/src/broadcast/queue.ts),
[queue/pure.ts](../../controller/src/broadcast/queue/pure.ts), настройки — ниже

Апстрим выбирает следующий трек в момент, когда кончается текущий, — `upcoming`
почти всегда длиной 1. Отсюда «в админке нечего показывать» и «заказу некого
обгонять».

Настройка `queue.lookahead` — 1–10, по умолчанию **1** (поведение апстрима); на
станции **5** ([патч настроек](../onboard/patches/2026-09-22-queue-lookahead.json)).
Потолок 10 не технический, а честный: каждый трек стоит своего вызова агента и
выбран по правилам **текущего** часа — к десятому шагу этот час уже чужой. Новая
настройка заводится во всех местах сразу, и пропуск любого молчалив:

| Где | Что |
|---|---|
| [schemas/settings.ts](../../controller/src/schemas/settings.ts) | `QUEUE_LOOKAHEAD_BOUNDS`, `queuePatchSchema` |
| [settings/patch-registry.ts](../../controller/src/settings/patch-registry.ts) | `queue` в `SETTINGS_PATCH_KEYS` и в карте схем — **без этой строки `POST /settings` отбрасывает блок молча** |
| [settings/defaults.ts](../../controller/src/settings/defaults.ts) | дефолт `queue.lookahead: 1`, `BOUNDS.queueLookahead` |
| [settings.ts](../../controller/src/settings.ts) | нормализация хранимого (дробное округляется, вне границ — дефолт) и применение патча; читается вживую, без рестарта |
| [routes/settings/core.ts](../../controller/src/routes/settings/core.ts) | `queue` в ответе `GET /settings` — иначе настройку нечем прочитать обратно, и `onboard.py --patch` честно скажет «не применилось» |

Один инвариант апстрима правка ломает **намеренно**:
`scripts/settings-patch-schema.test.ts` перечисляет ключи настроек со схемами, и
`queue` в него добавлен. Тест не устарел — он для того и написан, чтобы новый ключ
был замечен.

### Добор очереди

`runPickCycle` получил флаг `topUp`. Добор начинается в `onTrackStarted`, когда
очередь не пуста, но мельче цели (`topUpWanted() > 0`), а дальше цепляется из
`finally` самого цикла. Три условия, каждое обязательное:

- **добор идёт по одному.** `runPickCycle` — один вызов LLM-агента, другого способа
  выбрать трек у станции нет. Глубина 5 стоит до пяти вызовов;
- **повтор — только если очередь выросла.** Неудачный пик (LLM недоступен, пул пуст)
  иначе превратился бы в бесконечную череду вызовов;
- **добранный трек следует за хвостом очереди**, а не за тем, что играет: якорь пика
  (`pickAnchorItem`, в v1.8 — `predecessorItem`) — последний элемент очереди. Иначе
  контекст пика описывал бы стык, которого не будет; в журнале это видно по
  обоснованиям вида «keeps rock energy after Stones». Прогноз и событие пика
  строятся от того же якоря — чистая `pickAnchorFrame` в `queue/pure.ts`: `leadSec`
  — остаток текущего плюс длительности **всех** элементов очереди до якоря
  включительно (до правки — только самого якоря, и граница шоу для пика считалась
  на несколько треков раньше), а `anchorPrior` в `runTrackEvent` («after "…"» в
  тексте события) — элемент перед якорем, либо текущий трек, если якорь — голова.
  Для пути дедлайна, где якорь — придержанная голова, оба ответа прежние. Трек
  неизвестной длины среди них — прогноза нет (`null`), как у `pickLeadSec`.

Добор идёт **молча**: `wantLink` при `topUp` не считается — линк, написанный за
четыре трека до эфира, нёс бы ложные `linkPrev` и `linkClockAt`. Подводку пишет стык
(следующий раздел).

**Передачу микрофона добор выпускает, только если в очереди одни авто-пики.**
Ждущую передачу (`session.pendingHandoff()` после смены сессии) выпускает цикл пика.
Апстрим зовёт его на **пустой** очереди, поэтому заказ или блок студии в очереди
передачу придерживают — mic-pass между треками одной записи хуже всего (правило
корневого `CLAUDE.md`). Добор зовёт тот же цикл на непустой очереди: блок пересёк
границу, сессия сменилась, в новом шоу `topUpWanted()` видит `sameShow`, и как только
в очереди меньше `lookahead`, добор выпускал прощание и приветствие, хотя впереди
ещё треки блока. Теперь цикл с `topUp` выпускает передачу, только когда каждый
элемент `upcoming` — авто-пик (`aiPicked`): такие пики апстрим ещё не выбрал бы, то
есть видел бы пустую очередь. Есть заказ или трек студии (`requestedBy`) — передача
ждёт, в будке строка «Show handoff held — …». Правило — чистая
`handoffMayAirFromCycle` в `queue/pure.ts`; на `QueueItem.block` оно не смотрит
(воздушный путь от него не зависит). Не застревает: после блока в очереди одни
авто-пики, и следующий цикл добора передачу выпускает; если добор не нужен и
очередь опустела, выпускает обычный цикл на пустой очереди, как у апстрима.
Устаревшую передачу по-прежнему снимает `runPersonaHandoff` (`HANDOFF_MAX_AGE_MS`).
Цикл без `topUp` (пустая очередь, дедлайн придержанной головы, повтор после
нерезолвленного пуша) ведёт себя как у апстрима. Взведённую передачу финального
трека это не трогает: её выпускает `runArmedBoundaryHandoff` по подтверждённому
старту трека, а цикл пика её и так пропускает (`boundaryHandoffAwaitsTrack()`).
Проверено `scripts/queue-handoff-topup.test.ts` — настоящий `runPickCycle` (подделаны
модель и погода, голос станции выключен — выпущенная передача сразу помечается
прозвучавшей): три трека блока после смены шоу при `lookahead` 5 — сессия
сменилась, передача ждёт; заказ слушателя в очереди — ждёт; одни авто-пики —
выпущена (RED → GREEN: передача уходила при треках блока впереди).

Правило «добирать или хватит» — чистая функция `topUpDepth` в `queue/pure.ts`:
глубина из `lookahead` (нечисло или меньше 1 — 1, дробное — вниз), переполненная
заказами очередь добирается нулём (повод перестать выбирать, а не удалять), за
границей шоу добор встаёт — но **первый** трек добирается всегда: пустая очередь —
это провал на авто-плейлист.

**Граница шоу.** `topUpWanted()` считает момент выхода добираемого трека в эфир:
остаток текущего плюс длительности всей очереди (`pickLeadSec`) плюс
`PICK_SHOW_LOOKAHEAD_SEC`, — и сравнивает `settings.resolveActiveShow` в этот момент
с текущим шоу. Источник тот же, что у контекста самого пика: два разных ответа на
«какое сейчас шоу» уже расходились (#1205). **Проверено тестом, не эфиром**: живого
перехода через границу шоу с глубокой очередью не наблюдали. В час перед сменой шоу
очередь короче пяти — это правильно, а не сбой.

**Длительности добора — к эфиру, а не по тегу.** Обе суммы — `leadSec` в
`pickAnchorFrame` и очередь в `topUpWanted` — должны считать каждый элемент так, как
он прозвучит: после потолка длины (#447; заказы от него свободны) и обрезки тишины.
Пока они берут сырой `knownDurationSec`, и длинный микс под потолком сдвигает границу
шоу на часы. Апстрим исправил то же для одного якоря (#1753, в `develop`, не в релизе):
`heldPlayableSec(item)` в `queue.ts` поверх чистой `heldAnchorPlayableSec`. **При
слиянии** с ним не брать ни одну сторону целиком — в обеих суммах длительность
элемента берётся через `this.heldPlayableSec(i) ?? 0` (0 сохраняет «длина неизвестна →
прогноза нет»); одна сторона теряет либо C03, либо поправку апстрима.

### Придержанный слив — без него глубина бессмысленна

`drainToLiquidsoap` отдаёт трек Liquidsoap, как только тому есть преемник. При
глубине 5 четыре трека из пяти уехали бы в `dj_queue` — а там заказ их уже не
обгонит (`push()` вставляет перед первым **несданным**), и отмена превращается в
отзыв по rid. Поэтому `Queue.DRAIN_AHEAD = 1`: в `upcoming` не больше одного `sent`,
очередь глубокая на нашей стороне, где её ещё можно переставить и подрезать. На
v1.8 проверено на живой станции: `sent: true` ровно у одного элемента из пяти.

**Принудительный слив минует только pair-hold, а не глубину.** У
`drainToLiquidsoap(force)` два вызывающих, и каждому нужно ровно своё:

| Кто | `force` | Что уходит в обход удержаний |
|---|---|---|
| `commitBeforeSkip` (пропуск трека оператором) | `true` | голова очереди, на которую ляжет пропуск; уже отдана — ничего |
| clip-as-track guard в `onTrackStarted` (сработал трек, чей элемент не отдан) | сам этот элемент | он и всё несданное перед ним |

Всё, что за целью, сливается по обычным правилам, `DRAIN_AHEAD` в том числе. До
правки `force` пропускал и проверку глубины, и пропуск трека отправлял в
`dj_queue` всю очередь из пяти. Пока отправитель занят, принудительный слив
запоминается (`pendingForceDrain`, а элемент guard — в `pendingForceItem`) и
повторяется при освобождении. Если за одну занятость приходят две цели guard,
хранится та, что дальше в `upcoming`, — слив до неё покрывает и ту, что впереди;
цель, уже ушедшая из очереди, уступает оставшейся.

**Проверено.** `scripts/queue-lookahead.test.ts` (`topUpDepth`; `pickAnchorFrame` —
хвост считает всю очередь и следует за предыдущим элементом, голова — прежний
ответ, RED → GREEN), `scripts/queue-settings-cold-load.test.ts` — холодная загрузка
(`setCache(null)` + `load()`, как требует `controller/CLAUDE.md`): сохранённая
глубина 5 переживает рестарт, хранимые 2.7 / 0 / 11 / `'5'` / отсутствие дают
3 / 1 / 1 / 1 / 1, `GET /settings` отдаёт `values.queue.lookahead`; без блока
`queue` в `load()` падают все три теста,
`scripts/drain-force.test.ts` — настоящий слив с поддельным потребителем
`next.txt`: `force` при отданной голове ничего не шлёт; голову, придержанную
pair-hold (персона с `djMode`, `pairDrain` включён, преемника нет), обычный слив
держит, а `force` отдаёт; guard отдаёт сработавший элемент поверх `DRAIN_AHEAD` и
не трогает следующий; force, встретивший занятого отправителя, доходит до цели
после освобождения, а из двух отложенных целей остаётся дальняя (RED → GREEN —
с отключённым `force` и с перезаписью `pendingForceItem`). При переносе —

`settings*`, `*drain*` (182/182).

## Подводка на стыке при глубокой очереди

`C04` · [queue.ts](../../controller/src/broadcast/queue.ts) `maybeWriteSeamLink`,
[dj-agent.ts](../../controller/src/broadcast/dj-agent.ts) `writeSeamLink`

У апстрима линк рождается **только вместе с пиком**, а при глубокой очереди пик на
стыке не случается — ведущий замолчал бы на переходах, то есть глубина откатила бы
«ведущий говорит чаще».

`Queue.maybeWriteSeamLink` срабатывает в `onTrackStarted`, когда очередь не пуста и
обычного пика не будет:

- только при `queue.lookahead > 1` (исправлено по финальному ревью переноса). На
  глубине 1 — поведение апстрима — элемент, ждущий в начале трека, это придержанный
  парным сливом пик или заказ, и счётчик уже считает путь пика: стык, считавший его
  ещё раз, вдвое урежал реплики ведущей;
- гейты пика — `autoLink`, трек автономный (`source` — `auto` или `ai`), есть
  история, `djCallsAllowed()` — плюс включённый голос станции (`autoVoiceAllowed()`);
- пока ждёт передача микрофона (`session.pendingHandoff()`), стык молчит и счётчик
  не тратит: правило v1.17 «стык смены шоу принадлежит передаче» — то же, что
  `wantLink && !finalTrackHandoff` на пик-пути. Линк уходящего ведущего не может
  идти после передачи;
- счётчик `tracksUntilLink` — общий с пик-путём, поэтому частота реплик не меняется.
  Сбрасывается он при **попытке** записи — даже если `writeSeamLink` потом ничего
  не запишет (сбой модели, смена эпохи ведущего, эхо, устаревший элемент, линк
  обрезан до пустого): иначе упавшая LLM получала бы вызов на каждом стыке, а
  агрессивного повтора апстрим не допускает. Не тратится счётчик, только если
  писать нечего (всё отдано, в голове заказ или готовая реплика, нет
  предыдущего): он остаётся `≤ 0`, и пишет следующий подходящий стык, а не стык
  через целый интервал;
- линк пишется для **первого несданного** элемента: Liquidsoap его ещё не получил, и
  `introScript` успеет отрендериться, а элемент перед ним в очереди (или текущий
  трек) и есть то, после чего он зазвучит, — `linkPrev` правдив. Заказ и элемент, у
  которого реплика уже есть, пропускаются: вторая реплика просто заменила бы первую
  неуслышанной;
- вызов — fire-and-forget, как цикл пика: стык не ждёт LLM.

`djAgent.writeSeamLink` идёт через общий шов линка v1.17 `generatePickLink`: автор
фиксируется на вызове модели, реплика отменяется, если за время вызова сменилась
эпоха ведущего. Контекст — `speechClockContext` на прогнозе часов, плюс `lastLink`;
дальше `trimLinkToIntro` и `dropEchoedLink`. Время эфира («Approximate air time»)
модели предлагается только при `clockIsAirTime: !!airAt && speakClockAllowed()`, как
на пути пула: в v1.17 `verifiedContextPacket` больше не проверяет часы сам, это
делает вызывающий, и стык при переносе этот флаг не передавал — модели стыка время
предлагалось и при выключенных часах станции (исправлено по финальному ревью). Элементу ставятся те же поля, что
`push()` ставит линку: `introKind: 'link'`, `introPersona`, `introHostSpeech`,
`introSessionKey`, `introLabelChecked`, `linkPrev` — **объектом** `{id, title,
artist}`. На v1.8 `linkPrev` писался строкой id, и сторож устаревшего линка в
`airIntro` для стыка не работал; исправлено при переносе. Прогноз часов и рендер
голоса заранее — следующая фича.

Элемент захвачен **до** вызова модели, а вызов длится десятки секунд: за это время
элемент мог выйти в эфир, быть снят оператором или получить свою реплику (линк
пика, подводку заказа). Поэтому после ответа модели `writeSeamLink` проверяет
`queue.upcoming.includes(item) && !item.introScript` и при провале ничего не
пишет — ни полей, ни `persist`, ни рендера, а в журнал уходит `link-skip`
«Seam link dropped — "…" left the queue / got its own line…».

**Счётчик переживает рестарт.** Поле `tracksUntilLink` инициализируется при создании
синглтона `Queue` — при импорте, до `settings.load()`, — и получало интервал частоты
по умолчанию (1–9, изредка 10–15) вместо частоты персоны (`chatty` — 1–5), а в
`queue.json` не сохранялось. После каждой выкатки первая подводка могла ждать до
часа эфира. Теперь счётчик пишется в `persist()` рядом с `tracksSinceJingle`, а
`recover()` (он идёт после `settings.load()`) восстанавливает его чистой
`restoredLinkInterval` из `queue/pure.ts`: сохранённое число зажимается в границы
**текущей** частоты (`linkIntervalMax` — верх диапазона `pickLinkInterval`; персона
могла смениться, пока контроллер лежал), `≤ 0` остаётся «пора»; поле отсутствует
(`queue.json` до правки, свежая установка), `null` (так JSON пишет `Infinity`
молчащей персоны) и мусор дают свежий интервал по частоте персоны; молчащая
персона — всегда `Infinity`.

**Проверено.** `scripts/seam-link.test.ts` — элемент, ушедший из очереди или
получивший свою реплику за время вызова модели, линка не получает и не
сохраняется; стык, которому нечего писать, не тратит счётчик (RED → GREEN;
контроль — ждущий элемент линк получает, а счётчик сбрасывается при попытке).
`scripts/queue-request-pair.test.ts` — на глубине 1 стык счётчик не трогает, при
глубокой очереди считает (RED → GREEN). `scripts/seam-link-clock.test.ts` —
настоящий `writeSeamLink`, подменён только HTTP модели: при выключенных часах
станции время эфира в промпт не попадает, контроль — при включённых попадает
(RED → GREEN). `scripts/link-countdown-restore.test.ts` — очередь импортирована до
`settings.load()`, как в `server.ts`: рестарт без сохранённого счётчика берёт
интервал персоны, сохранённый переживает `persist()` → `recover()`, зажим в
границы частоты, молчащая персона, `linkIntervalMax` совпадает с верхом
`pickLinkInterval` по каждой частоте (RED → GREEN: после `recover()` оставалось
12 при `chatty`, в `queue.json` поля не было). При переносе —
`run-tests.sh --src`, `queue*`, `*link*`, `*host-speech*`, `*handoff*`,
`*boundary*` (175/175).

## Запрет подмены движка TTS

`C05` · [audio/tts-fallback.ts](../../controller/src/audio/tts-fallback.ts),
[audio/tts.ts](../../controller/src/audio/tts.ts)

В апстриме `tts.fallback.enabled = false` **декоративен**: он гасит только
операторскую ступень лестницы спасения, а сама лестница — настроенный движок →
`defaultEngine` → piper → kokoro, в v1.17 ещё и облачные провайдеры с Gemini — зашита
в `orderedFallbacks`. Станция с выключенным запасом всё равно договаривает фразу
голосом piper, и по замыслу апстрима это правильно («so the DJ never goes silent
because one provider hiccuped»).

Для станции, чей голос — клон конкретного человека, замысел обратный: **чужой голос
хуже молчания**. Ведущая посреди эфира превращается в синтезатор, причём бесшумно:
слушателю слышно «голос сбросился», а в журнале — `[tts] remote failed … — falling
back to piper`.

Правка — чистая функция `rescueForbidden(fallback)` и два её вызова. Оба нужны,
потому что к piper ведут **две** дороги:

| Где | Когда срабатывает | Что делает правка |
|---|---|---|
| `resolveEngine` | движок признан недоступным **до** синтеза (проба `/health`) | оставляет движок персоны, вызов честно бросает |
| `fallbackChain` | движок сорвался **в середине** рендера | возвращает пустую цепочку |

Пустая цепочка безопасна: `speak()` бросает, вызывающие ловят — очередь пишет `TTS
failed` и идёт дальше. Подводка не выходит в эфир, музыка не прерывается.

**По умолчанию подмены нет — на любой установке форка.** Блок `tts.fallback`
отсутствующим не бывает: `settings/defaults.ts` заводит его с `enabled: false`, а
`normalizeTtsFallback` при загрузке ставит тот же `false` вместо пропущенного или
небулева флага. Значит, станция, где про fallback никто не думал, при сбое движка
молчит, а не говорит голосом piper. Нужна лестница апстрима — `tts.fallback.enabled:
true` (тогда сперва настроенный запасной голос, затем `defaultEngine` → piper →
kokoro). Сравнение в `rescueForbidden` строгое (`=== false`), отсутствующий или
`null` блок запретом не считается — но это защитный край, а не поведение по
умолчанию: настройки такого блока не дают. В v1.17 новых путей подмены нет.

**Проверено тестом, не эфиром.** `scripts/tts-fallback.test.ts` — пять утверждений:
`enabled: false` (блок по умолчанию) — запрет, `enabled: true` и блок без флага —
лестница, отсутствующий и `null` блок (защитный край) — не запрет; при переносе —
`run-tests.sh --src`, `tts*` (70/70). Живой прогон требует оставить станцию без
подводок на время ожидания, поэтому ветка `resolveEngine` наблюдалась только в коде.
Что смотреть, когда случится: в `state/voice` не появляется файла с частотой
22050 Гц (piper), а в журнале — `TTS failed` **без** строки `falling back`.

Цена названа прямо: пока TTS недоступен, ведущая молчит совсем — станция играет
музыку без единой реплики, и снаружи это неотличимо от поломки. «Доктор» (Admin →
Doctor, `checkTts`) с 2026-10-25 говорит то же: при запрете подмены — «no fallback — the DJ
stays silent», а не апстримное «will fall back to Piper»
([«Находки авто-ревью 2026-10-24»](#находки-авто-ревью-2026-10-24)). На хосте станции F5
гасит контроллер карты, пока её занимает gemma4 (решение llm_routers 2026-10-09); на
прежней площадке, хосте GPU, ещё и до логона, когда там нет Docker вовсе.

### Гейт до генерации

Запрет решал дело на синтезе, то есть уже после модели. Пока мостик или F5 (с
2026-10-09 — на хосте станции, до того — на `<gpu-host>`) лежат, каждая подводка,
сегмент, интро заказа и бит программы сперва стоили вызова LLM и только потом падали
в `speak()` — ровно то, от чего апстрим предостерегает правилом «Gate before generation, not at the dispatcher». Навыки
`chat` и `curiosity` к тому же помечают прочитанным то, что так и не прозвучало.

Поэтому `autoVoiceAllowed()` ([voice-policy.ts](../../controller/src/broadcast/voice-policy.ts)) —
гейт, который уже спрашивают все места генерации, — закрывается и тогда, когда подмена
запрещена (`rescueForbidden`) **и** движок голоса ведущей заведомо недоступен
(`tts.personaEngineKnownDown()`). Это чтение кэша, без сети: проба `/health` удалённого
движка и так идёт раз в 30 с, а мостик отвечает на неё 503, пока F5 не загрузил модель.

- **«Заведомо» — главное слово.** Проба начинает с `false` до первого ответа; это не
  знание, и гейт открыт (fail-open) — иначе каждый старт контроллера начинался бы с
  немоты. Отсюда `known()` у общей [util/health-probe.ts](../../controller/src/util/health-probe.ts)
  и `remoteTts.availabilityKnown()`. Движки сайдкара tts-heavy (chatterbox, pocket-tts
  при `TTS_HEAVY_URL`) не сообщают, ответила ли их проба, — для них гейт не действует,
  как в апстриме.
- **Только при запрете подмены.** С `tts.fallback.enabled: true` реплику скажет другой
  движок, и писать её есть смысл.
- **Гейт генерации, не эфира.** Готовой реплике движок не нужен: `airIntro` и его
  зеркало в `airPendingVoice` (`boundaryCarriesTrackVoice`) спрашивают только выключатель
  `voiceEnabled()` ([queue.ts](../../controller/src/broadcast/queue.ts)). Иначе подводка,
  отрендеренная за секунды до падения, пропадала бы на стыке. Предрендер на сливе
  остаётся на `autoVoiceAllowed()`: синтез заведомо упадёт, а `airIntro` дорендерит по
  скрипту, если движок к эфиру вернётся.
- Ручные триггеры гейт минуют, как и выключатель голоса; пики и заказы идут как шли,
  заказ — без голосового интро.

Тупика «молчим, потому что разбудить некому» нет. Аренду слота (`/ensure-up`) мостик
берёт на каждый `/speak`, а пока гейт закрыт и `/speak` нет, — из неудачного `/health`:
в фоне, не чаще раза в `HEALTH_LEASE_EVERY` (60 с) и только в `HEALTH_LEASE_WINDOW`
(30 мин) после последнего `/speak`, чтобы ночью без слушателей выгнанный слот не
будился круглые сутки ([README мостика](../tts-bridge/README.md)). Дальше слот `tts`
возвращает сам пульт: он резидент (после OOM F5 — около минуты). И в апстриме с
включённой лестницей удалённый движок не зовётся, пока `/health` говорит «нет».

В журнале будки закрытый гейт выглядит как выключенный голос: крон навыка пишет
`stood down — the station voice is off (music only)` (текст апстрима). Настоящая
причина — строка `[remote] TTS endpoint unavailable` в логе контроллера.

**Директор тратит пол частоты на неудачной попытке**
([skills/_agent.ts](../../controller/src/skills/_agent.ts), `agenticTick`). Гейт ловит
известное падение, но проба отстаёт до ~35 с, а синтез падает и при здоровом `/health`
(OOM F5 посреди фразы). `agenticTick` не трогал `lastAnySegment`, если `announce` не
принял реплику, — и модель звалась на каждом такте директора: раз в 5 минут вместо 15 у
`moderate`. Теперь пол тратят и неудачная доставка, и настоящая ошибка (провайдер упал,
совместный сегмент не отрендерился) — по образцу счётчика стыка (C04). Кулдаун навыка
не тратится: в эфир ничего не ушло. Молчание модели — решение, а не попытка: после
него директор спрашивается на следующем такте, как в апстриме.

**Проверено тестом, не эфиром.** `scripts/voice-engine-gate.test.ts` (RED на main:
движок заведомо лежит — `autoVoiceAllowed()` всё равно `true`): проба без ответа —
гейт открыт; движок вернулся или лестница разрешена — открыт; готовая подводка выходит
в эфир при лежащем движке (мутация — `airIntro` на `autoVoiceAllowed()` — валит тест).
`scripts/segment-floor-failure.test.ts` (RED: после неудачного рендера модель звалась
на следующем же такте): провал рендера и ошибка провайдера тратят пол, молчание — нет.

## Потолок окна повторов 2000, журнал 6000

`C06` · [settings/vocab.ts](../../controller/src/settings/vocab.ts),
[config.ts](../../controller/src/config.ts), [queue.ts](../../controller/src/broadcast/queue.ts)
`recover()`

Жёсткий запрет на повтор — `llm.noRepeatWindow`: последние N **различных**
проигранных треков не вернутся в эфир ни одним путём выбора. У апстрима он зажат
двумя числами, и оба малы для коллекции в 4631 трек:

| Где | Апстрим | Форк | Почему |
|---|---|---|---|
| `settings/vocab.ts::clampNoRepeatWindow` | 1000 | 2000 | потолок настройки |
| `config.ts::queue.recentPlaysMax` | 2500 | 6000 | длина журнала `recent-plays.json`, из которого окно питается |

**Править надо оба.** Окно длиннее журнала молча усекается — комментарий апстрима к
`clampNoRepeatWindow` прямо связывает эти числа. Поднять потолок, забыв про журнал,
значит получить настройку, которая показывает 1736, а работает как «сколько журнал
помнит». 6000 записей — около одиннадцати суток при ~550 проигрываниях в сутки,
~700 КБ JSON, переписываемого на каждое проигрывание.

Настоящий ограничитель после правки — не потолки, а `effectiveNoRepeatWindow`: он
зажимает окно по **37.5% размера библиотеки** (`NO_REPEAT_MAX_LIBRARY_FRACTION`),
то есть 1736 треков при 4631. Это задуманный апстримом предохранитель — он оставляет
пикеру свежий пул и масштабируется с коллекцией сам; до правки его роль играл грубый
потолок 1000. На станции окно — 1736
([патч настроек](../onboard/patches/2026-09-22-no-repeat-window.json)).

**Журнал режется по числу записей, а не по возрасту** (третье место, исправлено по
финальному ревью переноса; [queue.ts](../../controller/src/broadcast/queue.ts)
`recover()`). Загрузка `recent-plays.json` при старте отбрасывала записи старше 96 ч —
около 1440 при темпе станции, меньше окна 1736 и потолка 2000: после каждого
рестарта окно сутки было короче, и могли повторяться треки 4–5-дневной давности.
Теперь отсечка только `recentPlaysMax`. Вместе с этим поле окна в админке поднято
до `max` 2000 ([web-changes.md](web-changes.md), «Поле окна повторов в админке»):
с прежним `max` 1000 стрелка поля сбрасывала 1736 в 1000.

**Что это даёт в эфире.** При темпе ~370 треков в сутки 250 (дефолт апстрима) — это
16 часов памяти: песня, услышанная вечером, законно возвращается к следующему
вечеру. 1736 — **4.7 суток**. Замер до правки: 210 повторов за 4 дня на 1493
проигрывания, 82 из них в интервале 12–24 часа.

**Чего правка не делает.** Окно артиста — отдельная фича
([«Окно артиста в агентном пути»](#окно-артиста-в-агентном-пути)). Пул кандидатов
окно не расширяет: за охват отвечает разметка библиотеки, а не память о сыгранном.

**Проверено.** `scripts/recent-plays-boot.test.ts` — журнал из 2000 записей с шагом
4 мин целиком переживает `recover()`, самая старая (≈5.5 суток) остаётся в окне
(RED → GREEN: 1440). Потолки 2000/6000 своим тестом не закреплены. При переносе —
`run-tests.sh --src`, `*repeat*`, `*vocab*`, `*recent*`, `settings*` (123/123);
апстрим сохранил 1000/2500, комментарии переписаны с пометкой `Fork:`.

## Заказ ищет по всей полке (requestPath)

`C07` · [picker/scope.ts](../../controller/src/llm/internal/tools/picker/scope.ts),
[picker/tools/search-library.ts](../../controller/src/llm/internal/tools/picker/tools/search-library.ts),
[dj-agent.ts](../../controller/src/broadcast/dj-agent.ts) `runRequestViaAgent`

Из-за отсутствия этой правки станция месяц отвечала «нашёл» и ставила не то.

Инструменты подборщика (`llm/internal/tools/picker/`) писались под **подбор музыки в
слот**, и их умолчания настроены на разнообразие: `collect()` отдаёт агенту 8 треков
и **не больше 3 одного артиста**, в порядке freshness-перетасовки, а `searchLibrary`
вдобавок читает **случайную** страницу выдачи (0/25/50). Заказ ходит через те же
инструменты и получает ту же выборку, хотя задача у него обратная: не «что-нибудь
подходящее», а «ровно эта песня».

В журнале станции 21–22.09 это выглядело так. На «Включи Агата Кристи — На войне»
агент искал `Агата Кристи`, получал **3** трека из **103** и ставил в эфир «Вечную
любовь»; на «rammstein - ich will» — 4 из 18 и «Sonne». Песни лежали в коллекции всё
это время; Navidrome по полной строке находит их с первого раза.

Одно поле области видимости — `PickerScope.requestPath` — меняет три умолчания:

| Где | На пике | На заказе |
|---|---|---|
| `scope.ts::collect` — `cap` | 8 | `REQUEST_CAP` = 120 |
| `scope.ts::collect` — `maxPerArtist` | 3 (строгий плейлист — без потолка) | `REQUEST_CAP` |
| `search-library.ts` — страница | 25 строк со случайного смещения | 200 строк с нулевого |

Поле заводится в `PickerScope` и в `NO_SCOPE` (умолчание `false` — пик-путь не
меняется ни в чём), а ставится единственным местом: `pickerScope({ recentIds,
requestPath: true })` в `runRequestViaAgent`. Это тот приём, которым файл просит
заводить любое новое ограничение, — одним полем в одном объекте. В v1.17 цепочка
`maxPerArtist` у апстрима выросла (строгий плейлист снимает потолок артиста) —
заказ в ней стоит первым.

**Потолок именно 120, а не «снять совсем».** Строки кандидатов становятся входными
токенами агента, и безлимитная выдача на широком запросе («включи что-нибудь») —
счёт за пустое место. 120 покрывает самую длинную полку коллекции (103 трека одной
группы) с запасом.

Замер на живой станции после правки (v1.8): `searchLibrary{"query":"Rammstein"}` →
**14** кандидатов вместо 4 (18 минус недавно игравшие), «Включи Агата Кристи - На
войне» → в эфир «Как на войне», «rammstein - ich will» → «Ich Will». Агент вдобавок
стал **уточнять** запрос вторым вызовом (`Rammstein Ich Will` → 1), чего при выборке
из трёх делать было незачем.

**Чего правка не делает.** Она не учит агента складывать запрос из артиста и
названия — это его решение, и иногда он по-прежнему ищет одним словом. Правка лишь
убирает то, что делало такой поиск **бесполезным**: в выдаче вся полка артиста.

**Проверено.** Своего теста нет. При переносе — `run-tests.sh --src`, `picker*`,
`request*`, `*search*`, `*scope*` (72/72).

## Окно артиста в агентном пути

`C08` · [dj-agent/artist-guard.ts](../../controller/src/broadcast/dj-agent/artist-guard.ts),
[dj-agent.ts](../../controller/src/broadcast/dj-agent.ts) `pickViaAgent`,
[queue.ts](../../controller/src/broadcast/queue.ts) `queuedArtistRoots`

Жалоба была «за день много раз Агата Кристи и Наутилус», и разбор журналов станции
(v1.8, 19–22.09) показал, что дело не в коллекции:

- основным путём выбора стал LLM-агент (0 → 28 → 75 → 66% пиков, до того вёл
  `explore`). Агент брал из **194** артистов, `explore` — из 697; доля топ-10 в его
  выборах 38–50% против 18–22%;
- окна артиста по часам (`recencyWindowsForLibrary`: 2 ч × 1.5 на 3k+ треков = 3 ч)
  у агента не было вовсе: `picker/scope.ts::collect` сознательно не передаёт
  `recentArtists` (#618 — вырезка артистов из выдачи оставляла инструментам
  похожести ~1 кандидата на узких каталогах);
- итог: агент 74 раза обосновал выбор словами «new artist», и в 32 из них артист
  звучал 8–155 минут назад. Медианный интервал Агаты Кристи — 1.2 ч против 2.9 ч без
  агента, минимальный — 8 минут.

**Что сделал апстрим и чего не хватило.** v1.9 (#1406/#1433) дал агентному пути
разнесение артистов по **слотам** — `llm.artistVarietyWindow`, по умолчанию 5
последних плюс очередь, — и сделал его **мягким**: нет кандидата свежее — пик
остаётся. Окна по часам библиотеки у агента так и нет. Форк кладёт его поверх
апстримного `runArtistGuard`, в точку выбора, а не в инструменты, поэтому #618 не
возвращается:

- `artistWindowRoots(queue.recentArtistsSince(windows.artistHours), neighbourRoots,
  queue.queuedArtistRoots())` — ключи окна: сырые имена из журнала проигрываний,
  приведённые к ведущему артисту (#1251: `X feat. Y` — это X), плюс **вся** очередь
  несыгранного — при `queue.lookahead = 5` пик ложится в хвост и выйдет в эфир
  после неё. Именно вся: `neighbourRoots` (`neighbourArtistRoots(artistVarietyWindow)`)
  берёт только хвост `upcoming.slice(-n)`, а при окне 0 — ничего, и при
  `lookahead` глубже окна голова очереди выпадала из окна артиста — добор мог
  выбрать артиста, который уже стоит в очереди. `queuedArtistRoots()` читает весь
  `upcoming`, как `recentAlbumKeys`; мягкие слоты апстрима по-прежнему смотрят хвост;
- `runArtistGuard` получает их необязательными `windowRoots`/`windowHours`; без этих
  полей поведение апстрима не меняется ни в чём;
- причина `window` старше мягкой `recent` (но не `onair` — совпадения с якорем пика)
  и **жёсткая**, как было на v1.8:

| Причина | Когда | Перевыбор | Не из чего перевыбрать |
|---|---|---|---|
| `onair` (апстрим) | артист выбора — артист якоря пика | кандидаты без этого артиста | спасение пулом |
| `recent` (апстрим, мягкая) | артист в последних N слотах | кандидаты свежее | пик остаётся |
| `window` (форк, жёсткая) | артист звучал в окне по часам или стоит в очереди | кандидаты вне окна **и** без артиста якоря | **сразу** спасение пулом; пул держит окно артиста сам |

Откат различается намеренно. У `window` «голый» набор (`alternativeCandidates` при
исчерпании отдаёт кандидатов без фильтра) может содержать артиста якоря: избегая
повтора через два часа, страж поставил бы повтор подряд. Поэтому исчерпанный набор
не предлагается вовсе. Пул тоже пуст — пик остаётся с пометкой `(relaxed)`.

**Пул держит окно и по очереди** ([music/picker.ts](../../controller/src/music/picker.ts)
`pickViaPool`, исправлено по ревью пачки). Спасение пулом — и откат агента на пул —
полагаются на окно пула, а тот брал артистов только из `recentArtistsSince`
(сыгранные и текущий): при глубоком `lookahead` пул мог выбрать артиста, который уже
стоит в очереди. Теперь в тот же набор `recentArtists` идут артисты всего
`upcoming` — сырые ключи (`artistKey`, сравнение сырое с сырым, как у сыгранных) и
ключи ведущего артиста (`queue.queuedArtistRoots()`, чтобы `X & Y` в очереди не
пропускал `X`). Набор тот же, что и раньше, — смягчаемый: если в очереди все
артисты пула, каскад `filterPickerCandidates` снимает окно артиста, и пул всё равно
выбирает (never-starve). Проверено `scripts/pool-artist-window-queue.test.ts` —
настоящая `library.db`, подделаны Navidrome и модель: артист из очереди (и ведущий
артист дуэта из очереди) выпадает из пула (пул 1 из 4), при всех артистах в очереди
пул остаётся 4 (RED → GREEN: пул 4).

**Заказы вне окна.** Страж живёт в `pickViaAgent`; заказ идёт через
`runRequestViaAgent` и его не проходит — слушатель, трижды попросивший Агату Кристи,
её и получит. Настройкой окно не меняется: его размер считает
`recencyWindowsForLibrary` от размера коллекции.

**Цена.** Каждое срабатывание `window` — лишний вызов модели (перевыбор из
кандидатов своего прогона) либо пик пулом. Сколько их на деле — видно в журнале
событий `state/logs/events-YYYY-MM-DD.jsonl`: `pick.artistGuard` с `"cause":
"window"` (`basis: "artist-hours"`); в журнале контроллера — `recently-played artist
"X" (heard within 3 h) avoided — …`.

Апстримный диагностический тест `scripts/pair-drain-interleaving.test.ts` переписан:
тот же повтор артиста из заказа, но теперь сначала спасение пулом, и строка
называет окно, а не слоты. Имя теста — по сути проверки: «…puts the candidate
inside the artist window, and the empty pool rescue lets it stand» (было апстримное
«…soft spacing repeat»).

**Проверено.** `scripts/artist-guard-run.test.ts` — пять тестов окна (перевыбор,
спасение пулом при исчерпании, артист якоря не возвращается, сорванный перевыбор
идёт в пул, окно старше слотов; RED → GREEN при переносе),
`scripts/artist-guard.test.ts` — ключи `artistWindowRoots` и `queuedArtistRoots` (вся
очередь, голова тоже), `scripts/artist-window-deep-queue.test.ts` — настоящий путь
`runTrackEvent` → `pickViaAgent` → `runArtistGuard` (подделан только
`pickerAgent.run`): очередь из десяти, артист на первой позиции, окно слотов 5 и 0 —

## Стык — прогноз часов и голос заранее

`C09` · [queue/pure.ts](../../controller/src/broadcast/queue/pure.ts) `seamLinkShowAt`,
[dj-agent.ts](../../controller/src/broadcast/dj-agent.ts) `writeSeamLink`

Разбор 2 ч 23 мин живого журнала 22.09 (v1.8) показал две поломки подводки на стыке,
обе беззвучные — наружу это выглядело как «ведущий стал молчаливее».

**Часы уходили на две минуты назад.** `linkClockAt()` читает аргумент как `showAt`
пик-пути (`now + lead + PICK_SHOW_LOOKAHEAD_SEC`, 120 с) и вычитает запас обратно.
Стык передавал `now + lead` без слагаемого, реальный выход наступал на 110–111 с
позже прогноза при `LINK_CLOCK_DRIFT_TOLERANCE_SEC` = 90 — и `airIntro` ронял линк
как «часы соврут»: 6 из 10 написанных и оплаченных токенами реплик не прозвучали.
Прогноз теперь собирает чистая функция `seamLinkShowAt(leadSec, now)` от
`queue.remainingUntilItemAirs(item)`, а не от остатка текущего трека: за уже
отданным Liquidsoap элементом эти числа расходятся на целый трек. Штамп
`linkClockAt` ставится, только если часы ведущему **предлагались**
(`linkClockStampFor(airAt, speakClockAllowed())`), как на пик-пути: реплика под
запретом часов времени не называет, и сторож дрейфа не должен её ронять.

**Голос рендерился в момент выхода трека.** Слив отдаёт элемент Liquidsoap в том же
тике вотчера, в котором срабатывает стык, — задолго до того, как вернётся LLM.
Предрендер слива поэтому не видел текста, и WAV синтезировался в `airIntro`: ведущий
заговорил на 21-й секунде песни, а занятый TTS отвечал 503, и реплика пропадала.
Текст известен за 146–513 с до стыка, поэтому `writeSeamLink`, если элемент уже
отдан, сразу зовёт `queue.startIntroRender(item)` и сохраняет очередь. Это учтённый
предрендер апстрима (v1.13–v1.17, #1409): он снимает «личность» реплики, так что
подменённая тем временем реплика этот WAV не получит, а опоздавший рендер всё равно
достаётся `airIntro`. Несданный элемент по-прежнему рендерит слив, по своему бюджету
времени. Собственный `prerenderIntro` из v1.8 при переносе не нужен.

Сопоставление правила Folder — по границе `/`: `…/Hits` не задевает `…/Hits 2`; трек
без настоящего пути не подпадает ни под что (недоблокировка видна по счётчику).
Таблица жанров папок лежит рядом с `blocklist.json`, а не в `library.db`, чтобы её не
стёрли Library → Reset/Reconcile. Веб-сторона (дерево папок, карточка жанров
папок) — W12 в [web-changes.md](web-changes.md).

**Миграция — проверка колонки, а не номер.** На v1.8.0 колонка `path` была
миграцией 21; апстрим в v1.9–v1.17 занял 21–27. Теперь в
[schema.ts](../../controller/src/music/library-db/schema.ts) после всей цепочки
апстрима стоит идемпотентная проверка: `PRAGMA table_info(tracks)`, и `ALTER TABLE
tracks ADD COLUMN path TEXT` — только если колонки нет. `user_version` она не
трогает, так что следующая миграция апстрима может взять любой номер.

Переход базы, которую вела сборка форка на v1.8.0, — без ручного шага. Там
`user_version = 21` (наша прежняя миграция), а у v1.17 под номером 21 —
`era_untrusted`, и блок `userVersion < 21` молча не выполнился бы вместе с 22–27.
Поэтому `migrate()` первым делом узнаёт подпись такой базы — `user_version = 21`,
колонка `tracks.path` есть, `era_untrusted` нет — и откатывает `user_version` на 20
(в журнале `[library-db] v1.8-fork database … rewinding to 20`): миграции 21–27
апстрима проходят, а проверка в конце видит колонку `path` и ничего не делает. Это
касается и базы, восстановленной из бэкапа времён v1.8. База апстрима на 21 несёт
`era_untrusted` и под подпись не попадает.

**Путь даёт флаг плеера Navidrome.** Без Report Real Path у плеера `sub-wave [node]`
Navidrome отдаёт станции поддельный путь `Артист/Альбом/Трек`, и ни правила Folder,
ни жанры папок ничего не видят. Строку плеера Navidrome заводит на каждое сочетание
«пользователь + клиент + User-Agent», поэтому строк `sub-wave [node]` может быть
несколько; важна строка учётки, под которой ходит контроллер (`NAVIDROME_USER` в
`.env` стека). Флаг живёт в базе Navidrome, а не в конфиге: заведёт Navidrome новую
строку плеера (другой User-Agent, переустановка) — флаг будет выключен, и на вкладке
Blocked появится «N tracks have no real path». Сохранённые пути при этом не пропадут:
поддельный путь колонку не затирает. Включается в Navidrome: аватар → Players →
`sub-wave [node]` нужной учётки → Report Real Path.

**Путь абсолютный** (`<music-mount>/…`): Navidrome (проверено на 0.63.2) отдаёт
`filepath.Join(LibraryPath, Path)`. Смена точки монтирования обнулит правила Folder и
жанры папок — видно по счётчикам.

**Пик агента несёт только id.** AI-пики доходят до `queue.push` и `purgeBlocked`
через `trackFields()`, который снимает путь и жанры, поэтому `trackPath` и
`trackGenres` добирают их через `library.get(id)`. Из `slimTrack` путь при переносе
убран: v1.17 строит её из урезанной проекции пула без пути.

**Сверка не выкидывает заблокированные треки, и это держится на одной детали.**
`subsonic.iterateAllSongs` пропускает песни через фильтр блокировки
(`blocklist.rejectBlocked`), но дочерний процесс сверки (`tag-library.ts
--reconcile-only`, его запускает `broadcast/tagger.ts`) блок-лист не загружает и
видит все треки. Загрузить блок-лист в дочернем процессе — значит заставить сверку
удалить строки заблокированных треков из `library.db`.

**`Other` — не жанр для станции.** Navidrome тег `Other` жанром не считает, поэтому
треков без жанра для станции на 4 больше, чем в тегах файлов.

**Жанр передачи, заданный только папкой.** Жанр передачи разрешался через
`subsonic.resolveGenreName`, а тот знает только теги из `getGenres`. Жанр, назначенный
лишь папке, не разрешался, и замок снимался целиком («the genre filter is OFF» —
строгая передача играла всю библиотеку), хотя `trackGenres` жанр папки читает. Мало
разрешить: источники передачи (`getRandomSongs`, `getSongsByGenre`) — тоже Navidrome,
жанров папок не знают, и строгий авто-плейлист, который режет чужой жанр в каждом
источнике, мог остаться пустым. Поэтому в `folder-genre-show.ts` две половины:

- `resolveShowGenreName` — точный тег, затем точный (по `normGenre`) жанр папки, и
  только потом поиск по подстроке среди тегов. Жанр папки считается, лишь пока его
  читает хоть один незаблокированный трек — как тег существует, пока его несёт песня:
  устаревшее назначение (папку переименовали, треки получили теги) не держит замок
  над пустотой. Через него разрешают жанр передачи пул (строгий и мягкий), агент,
  авто-плейлист и счётчик кандидатов в редакторе передачи — все одинаково. Жанру
  папки Navidrome не нужен: если `getGenres` бросает (Navidrome лежит), жанр папки
  всё равно разрешается, а для любого другого жанра исключение пробрасывается как
  есть — вызывающие и раньше отбрасывали жанр, на котором упало разрешение, так что
  теговый жанр при лежащем Navidrome ведёт себя как у апстрима.
- `folderGenreTracks` — треки без тега, до которых жанр доходит через папку (тот же
  `genreMatches`, что у замка, по жанрам папки из `genresForPath`). Источник
  `show-genre` пула и авто-плейлиста кладёт их рядом с выдачей Navidrome — один и
  тот же вызов в обоих местах (апстрим держит их «keep in step»). Скан строк без тега
  с блок-листом поверх — синхронный, на event loop, и зовётся по нескольку раз на
  пик, поэтому он **кэширован** до изменения любого из трёх входов: записи в
  `library.db` (`changeToken`: `data_version` чужих соединений, `total_changes()`
  своего, смена дескриптора), таблицы жанров папок (её только заменяют целиком —
  версия это сама ссылка) и блок-листа (`blocklist.revisionToken()`: правка,
  включение/выключение правила по сезону или передаче, смена состава плейлиста в
  правиле). Таймера нет намеренно: блок-лист абсолютен, кэш, переживший блок, выпустил
  бы трек в эфир. Вызывающим отдаются копии: авто-плейлист штампует на треки `gainDb`.

Заказы слушателей, инструмент агента `songsByGenre` и генератор плейлистов остаются на
`resolveGenreName`: они берут треки у Navidrome, и имя жанра папки дало бы им пустой
ответ (спека, §3.3). Что меняется на станции: передачи «Поп»/«Рок» (это и теги, и жанры
папок) теперь получают треки папок и из своего источника, а не только случайно через
другие. И если жанр папки совпадает с жанром передачи точно, а тег — лишь подстрокой
(папка «Шансон», тег «Русский шансон»), замок встаёт на «Шансон»: он пускает и треки
папки, и тег «Русский шансон» (уточнение), но выдача Navidrome по «Шансон» пуста, так
что треки с тегом приходят только из других источников.

## Кириллица в именах артистов и в сверке MusicBrainz

После переноса, вне таблицы · [music/subsonic.ts](../../controller/src/music/subsonic.ts)

docker exec -w /app sub-wave-controller node -e '
  const db = new (require("better-sqlite3"))("/var/sub-wave/library.db");

## °, % и тире диапазона — английскими словами только в английской речи

`C14` · [audio/speech-text.ts](../../controller/src/audio/speech-text.ts) `normalizeForSpeech`

v1.17 (#1734, `186137fc`) читает годы словами — по-английски и только при английском
или пустом `persona.language`; при другом языке год остаётся цифрами для движка.
Остальные английские замены язык не спрашивали: `°` → `degrees` (`°C`/`°F` — `degrees
Celsius`/`Fahrenheit`), `%` → `percent`, `$5` → `5 dollars` (`$100k`, `$5M`, `$2bn`),
`mph` → `miles per hour`, `km/h` → `kilometers per hour`, `&` → ` and ` и тире между
цифрами → ` to ` (v1.15, `normalizeTtsPunctuation`). Русская ведущая отдавала F5
«влажность 80 percent», «в 1969 to 1972 годах», «собрал 5 dollars млн», а F5 читает
латиницу по русским правилам. Хуже всех `&`: словарь коллекции держит 76 имён с ним
(«al bano & romina power»), и после « and » ни одно не совпадало.

Форк считает предикат языка один раз в начале `normalizeForSpeech` (`english`) и
закрывает им все английские подстановки: годы (как у апстрима), `°`, `%`, `$`, `mph`,
`km/h`, `&` и тире диапазона. При неанглийском языке символы доходят до движка как
написаны, а русские слова с согласованием («восемьдесят процентов», «минус три градуса
по Цельсию», «пять миллионов долларов», «шестьдесят миль в час», «в тысяча девятьсот
шестьдесят девятом — … годах») делает служба F5 ([f5_numbers.py](../tts-f5/f5_numbers.py)),
а `&` в именах — её словарь коллекции. Английская и пустая речь — как у апстрима,
байт в байт.

**Без языка персоны правка не работает.** Пустой `language` апстрим считает
английским: годы уходят в F5 «nineteen sixty-nine», проценты — «percent». Станции
нужен `persona.language` — патч
[2026-10-09-persona-language.json](../onboard/patches/2026-10-09-persona-language.json)
(`onboard.py --persona p_ru --from …`). Значение — название языка, а не код: апстрим
подставляет его в английские промпты («You speak and write exclusively in Russian»);
при пустом там стоит English, вопреки `soul`. Выставленный язык меняет и другое:
служебная фраза диктора «This is X.» уступает место реплике модели на языке персоны
(`announce-line.ts`), превью голоса берёт русский образец.

**Проверено.** `scripts/speech-units-language.test.ts` — русский, `ru`, «русский»,
французский и турецкий оставляют `°`, `%`, `$`, `mph`, `km/h`, `&` и тире диапазона

## Поиск по библиотеке находит кириллицу

После переноса, вне таблицы ·
[music/library-db/lifecycle.ts](../../controller/src/music/library-db/lifecycle.ts) `open`,
[music/library-db/browse.ts](../../controller/src/music/library-db/browse.ts) `filter`

Третье латинское допущение апстрима после жанров (C12) и имён артистов — свободный
текстовый фильтр библиотеки. `filter()` приводит запрос к нижнему регистру в JS, а

`tracksLikeThisAudio` — когда зерно пришло названием, а не id.

`open()` регистрирует на соединении функцию `ulower` (`toLowerCase` из JS,
`deterministic`), и фильтр сравнивает через неё: обе стороны свёрнуты одним правилом, и
ASCII-ограничение `LIKE` больше ни на что не влияет. Сортировки (`ORDER BY LOWER(…)`) не
тронуты — там регистр кириллицы меняет только порядок строк. Цена — три вызова JS на
строку полного просмотра, который фильтр делал и раньше. Второе соединение с базой
(`id-rotation-journal.ts`) фильтр не зовёт. В записях авто-ревью 2026-10-10 этого
дефекта не было — он всплыл при их разборе. Правка годится апстриму как есть
(предложение не отправлялось).

## Сборка

Образ собирается на хосте станции из клона форка `~/radio`. Клон руками не правится:
его состояние — ровно та ревизия, которую доставили последней. Клон временный (~1 ГБ —
вся история апстрима): после сборки, тестов и выкатки — `rm -rf ~/radio`, следующий
`push-to-station.sh` создаст его заново.

### Доставка ревизии

С рабочей машины, из корня репозитория:

```bash
bash station/tools/push-to-station.sh <ref>     # по умолчанию HEAD
```

[push-to-station.sh](../tools/push-to-station.sh) берёт хост и SSH из
`station/.env` (`STATION_SSH`, `SSH_PORT`, `SSH_KEY`; шаблон — `station/.env.example`),
собирает `git bundle` из всех веток, тегов и самой ревизии, копирует его на хост и там:
заводит `~/radio`, если его нет, делает `fetch` из бандла, `checkout -f --detach <sha>`
и `git clean -fd`, печатает `station: ~/radio @ <sha>`. Доступа к приватному `origin`
хосту не нужно. Правки, сделанные в клоне руками, следующий вызов затрёт.

Ревизия едет в бандле временным ref-ом `refs/push-to-station/<pid>-<sha>` (удаляется
по выходу скрипта): коммит, достижимый только из detached HEAD или remote-tracking ref,
в `--branches --tags` не попадал, и `checkout` на хосте падал. Бандл на хосте —
`~/radio-<pid>-<sha>.bundle`, его удаляет `trap … EXIT` — и при сбое `fetch` или
`checkout` тоже, а не только при успехе. Имена свои у каждого запуска, чтобы два
параллельных вызова не подменяли и не удаляли их друг у друга; клон `~/radio` при этом
общий — из двух одновременных доставок в нём остаётся последняя.

Бандл, а не архив с рабочей машины, — из-за концов строк: дерево, приехавшее с
Windows с CRLF, роняет shell-тесты апстрима (`aio-log-link`, `instructions`,
`state-bootstrap`), и это выглядит как регрессия правки. Из бандла файлы выходят
такими, какими лежат в репозитории, с LF. Клон — в домашнем каталоге, не в `/tmp`:
там tmpfs, он ест ОЗУ хоста.

### Сборка образа под сторожем памяти

На хосте станции:

```bash
cd ~/radio && bash station/tools/guarded.sh sudo docker build \
  -f docker/Dockerfile.controller -t subwave-controller:1.17.0-ru \
  --label org.opencontainers.image.revision=$(git rev-parse HEAD) \
  --build-arg SUBWAVE_BUILD_VERSION=1.17.0-ru+$(git rev-parse --short HEAD) .
```

Метка `org.opencontainers.image.revision` — ревизия форка, из которой собран образ:
тег `<версия>-ru` один на все сборки, а метку читает [сверка перед
выкаткой](#перед-выкаткой--сверка-живого-образа-с-клоном). `SUBWAVE_BUILD_VERSION`
`Dockerfile.controller` кладёт в окружение, контроллер пишет её в манифест резервной
копии и бандла персон (без неё — версия из `package.json`); `+<sha>` делает видимой и
ревизию.

Хост станции делит ОЗУ с чужими службами, и память кончается у него раньше, чем у
cgroup контейнера: `tsc` однажды пять раз подряд уронил хост в глобальный OOM, и тот
забрал с собой соседние службы. Сборка образа идёт с `npm ci --omit=dev` внутри,
поэтому её тоже ведёт сторож. На хосте станции не запускать `tsc` и `npm ci` вне
образа вовсе (см. [station-pitfalls.md](station-pitfalls.md), «Сборка и образы», и
[правила форка](../../.claude/rules/radio.md)): тесты — в образе, линтер — на рабочей
машине.

[guarded.sh](../tools/guarded.sh) запускает команду и каждые полсекунды читает
`MemAvailable` из `/proc/meminfo`. Ниже `MIN_AVAIL` МБ (по умолчанию 500, меняется
переменной окружения) — печатает `GUARD MemAvailable N МБ — снимаю: <команда>` и снимает
команду: SIGTERM всей её группе процессов, а не завершилась за `GRACE` с (по умолчанию
10) — SIGKILL. В конце всегда печатает минимум `MemAvailable` за прогон. Код возврата —
код команды, либо **3** со строкой `GUARD снято: <команда>` — только если сигнал снятия
дошёл и команда после него завершилась. Не дошёл ни один — строка `GUARD снять не
удалось — команда доработала сама, код N` и код самой команды: «снято» про
доработавшую сборку было бы неправдой. Код 3 — не ошибка сборки: память хоста
кончилась, и сначала надо понять, кто её занял, а не повторять сборку подряд.

Почему группа и почему так. До 2026-10-09 сторож слал один SIGTERM процессу `sudo`,
стоя с ним в одной группе, а sudo не пересылает команде сигнал от процесса своей
группы — `docker build`, скорее всего, шёл дальше. Теперь команда запускается через
`setsid` (своя группа); сигнал группе идёт через `sudo -n kill` — процессы под sudo
принадлежат root, — а нет такого права в sudoers, то своими правами; не дошёл —
строка `GUARD не удалось послать SIG… — нет прав`. Жива ли команда, сторож смотрит по
`/proc/<pid>`, а не `kill -0`: процессу root тот отвечает «нет прав», и прежний цикл
мог счесть sudo завершённым с первого замера. Снятый клиент `docker build` должен
унести с собой и сборку в демоне: BuildKit отменяет сборку, чей клиент отключился (на
хосте станции не проверялось). Ctrl+C сторожу пересылается команде — в другой группе
она иначе пережила бы сторожа.

Проверка на хосте после изменения сторожа или sudoers:

```bash
MIN_AVAIL=999999 bash station/tools/guarded.sh sudo sleep 30; echo "код $?"
pgrep -af 'sleep 30'          # пусто
```

Ожидается: за секунду-две `GUARD снято`, `код 3`, `pgrep` пуст. Ждёт 30 с, пишет «нет
прав» и «снять не удалось» с кодом 0 — сигнал до `sudo` не доходит: нужен `kill` в
sudoers (NOPASSWD). Без sudo то же проверяет [test_guarded.py](../tests/test_guarded.py):
снятие с детьми — на Linux, код 3 против кода команды — и в Git Bash, на подменах
(`-m integration`: тесты дольше секунды).

копии.

Первая проверка — метка ревизии у живых контейнеров: выкатываемая ревизия (`HEAD`
клона) должна быть её потомком, иначе в новом образе нет чего-то, что уже в эфире:

```bash
for c in sub-wave-controller sub-wave-web; do
  rev=$(sudo docker inspect -f '{{with index .Config.Labels "org.opencontainers.image.revision"}}{{.}}{{end}}' "$c")
  if [ -z "$rev" ]; then echo "$c: метки нет — собран до неё, смотреть дифф ниже"
  elif git -C ~/radio merge-base --is-ancestor "$rev" HEAD; then echo "$c: $rev — предок, ок"
  else echo "$c: $rev — НЕ предок HEAD (или неизвестен клону) = стоп"; fi
done
```

Метка — только у образов, собранных командами из этого документа и
[web-changes.md](web-changes.md); у собранных раньше её нет. Вторая проверка, и
единственная для образа без метки, — дифф исходников живого контейнера с клоном; в нём
должны остаться только собственные новые правки:

```bash
cid=$(sudo docker create "$(sudo docker inspect -f '{{.Image}}' sub-wave-controller)")
sudo docker cp "$cid":/app/src ~/live-src && sudo docker rm "$cid"
diff -rq ~/live-src ~/radio/controller/src     # чужая строка здесь = стоп
rm -rf ~/live-src
```

### Тесты — в самом образе

Зависимости в образе уже стоят (`npm ci --omit=dev`), а раннеру (`tsx` и `node
--test`) другого не нужно. Прежний способ — `npm ci` в свежем `node:22` на каждый
прогон — занимал до 8–12 минут и на хосте, где памяти впритык, задевал соседние
службы. [run-tests.sh](../run-tests.sh) запускается с рабочей машины (Git Bash) и
уходит на хост станции по SSH; хост и ключ — из `station/.env` (нет файла — `TESTS_ENV`,
код 2):

```bash
bash station/run-tests.sh --patch                     # тесты, тронутые коммитами форка
bash station/run-tests.sh                             # весь набор в образе, ~130 с
bash station/run-tests.sh request-window              # файлы по подстроке имени
bash station/run-tests.sh --src /home/<user>/radio    # клон поверх образа
bash station/run-tests.sh --image <тег> …             # другой образ
```

- `--patch` — файлы `controller/scripts/*.test.ts`, которые трогают коммиты форка:
  `git diff --name-only UPSTREAM_BASE...HEAD`. Нет таких — `TESTS_ENV`, код 2. На v1.8
  такой прогон занимал ~25 с.
- `--src` — проверка рабочей ревизии **до сборки образа**: клон на хосте (после
  `push-to-station.sh`) монтируется только для чтения, `node_modules` берётся из
  образа ссылкой (`controller/node_modules → /app/node_modules` висит на хосте и
  оживает в контейнере), `STATE_DIR` уводится в `/tmp/state` контейнера. Это верно,
  пока `package-lock.json` клона совпадает с образом — коммиты форка его не трогают.
  С `--image ghcr.io/perminder-klair/subwave-controller:<версия>` ревизия проверяется
  на образе апстрима — так переносились фичи, пока своего образа новой версии ещё не
  было. Путь — абсолютный путь на хосте: `~` развернётся на рабочей машине.
- Контейнер ограничен 1.5 ГБ (`--memory`, `--memory-swap`); сторож на хосте снимает
  прогон при `MemAvailable` ниже 500 МБ (`TESTS_ENV … снят сторожем`), потолок прогона
  целиком — 900 с (`TESTS_TIMEOUT`); одному тесту — 120 с (`--test-timeout`). Замер
  30.09 (v1.8): хост не опускался ниже 4.1 ГБ.
- Раннер — `node --import tsx --test --test-concurrency=1`; нагрузочный
  `observatory-scale.test.ts` не запускается вовсе: сеет 200 тыс. треков в базу на
  820 МБ и идёт дольше двух минут.

**Судить по `TESTS_RESULT` и коду возврата, а не по нулю падений.** Падения
разбираются из сводки `failing tests:` в ключи `файл` или `файл :: тест` и сверяются
со списком известных в скрипте (шаблоны как в `case`): без `--src` — `KNOWN`, с
`--src` — `KNOWN_SRC`. Падение вне списка — «НОВЫЕ падения» и код 1; сводки нет —
прогон не дошёл до конца, код не 0; тесты, снятые по таймауту, печатаются строкой
`TESTS_TIMEOUT <ключ> after=120s`. Итог — `TESTS_RESULT pass=… fail=… skip=…`
(известные падения идут в `skip`). Разбор сверяется со счётчиком `ℹ fail N` сводки:
строк в списке `failing tests:` меньше N — значит, какое-то падение разбор не узнал, и
оно не попало бы ни в известные, ни в новые; такой прогон считается с новым падением
(`сводка: ℹ fail N, а … разобрано M`, код 1). Сверку и разбор итога над подставным
выводом проверяет [test_run_tests_known.py](../tests/test_run_tests_known.py).

Эталон — чистый v1.17.0:

- `KNOWN_SRC` — то, чего нет в самом образе, и потому падает и с `--src`:
  `gen-schemas.test.ts` (нужен `typescript`, devDependency) и
  `analyzer-python.test.ts` (нужны python-зависимости анализатора);
- `KNOWN` — `KNOWN_SRC` плюс среда образа: в нём нет каталогов репозитория (`web/`,
  `docker/`, `liquidsoap/`, `scripts/*.sh`, `docker-compose*.yml`), а часть тестов
  читает их или импортирует модули `web/`; с `--src` они проходят.

**В `KNOWN` — точные имена тестов, а «`файл :: *`» — только для файла, где падает
каждый тест.** В `show-boundary-drain`, `transition-effects`,
`settings-talk-placement-route`, `gemini-tts*` `web/` или `radio.liq` читают один-два
теста, а остальные гоняют `queue.ts`, `artist-guard.ts`, `routes/settings/core.ts`,
которые правит форк: «`:: *`» засчитывал известной и их регрессию — с кодом 0. Файлы
снимал прогон в образе (2026-10-05), точные имена — эмуляция образа на рабочей
машине (2026-10-09: из v1.17.0 только то, что копирует `Dockerfile.controller`, —
`package*.json`, `.npmrc`, `src/`, `scripts/`, — плюс `sounds/`) и чтение самих
тестов: падают ровно те `test()`, что читают названные каталоги. Падения самой
Windows (пути, `EBUSY` при удалении открытой базы) в список не идут. Выбор списка по
режиму, сопоставление и то, что каждое имя есть в исходнике теста, сверяет
[test_run_tests_known.py](../tests/test_run_tests_known.py) — функцией `is_known` самого
скрипта (без `bash` остаётся только сверка имён).

Пункт «`файл`» целиком — модуль, упавший на верхнем уровне. `test()`, объявленные до
места падения, идут и сверяются по именам; объявленные после в образе не
регистрируются вовсе — их проверяет только `--src` (в `jingle-play.test.ts` так
выпадают семь тестов ротации джинглов из `queue.ts`). **При переходе на новую версию
апстрима эталон снимается заново** ([«Обновление апстрима»](#обновление-апстрима)).

**Тесты апстрима, зависевшие от скорости машины, форк поправил, а не внёс в
`KNOWN`**: `KNOWN` прятал бы и настоящую регрессию. `queue-block-wiring` замораживает
часы (раздел C09). `generation-agent.test.ts` («…honors its tighter cascade
deadline») ставит модели дедлайн 40 мс и ждёт, что запрос дошёл до поддельного
сервера. Первый вызов в процессе отправляет запрос на хосте станции только через
~90 мс (ленивая сборка клиента провайдера) — дедлайн срывал его раньше, `calls` был 0,
3 из 3 и на чистом v1.17.0. Теперь перед проверкой идёт прогревочный вызов; тёплый
запрос уходит за 3–12 мс (замер 2026-10-05).

### Линтер и зеркало схем — на рабочей машине

`npm run lint` — это eslint **и** `tsc --noEmit`; он же ловит нарушение правила
«модуль схем импортирует только `zod`». devDependencies в образе нет, а `tsc` на хосте
станции уводит его в глобальный OOM, поэтому линтер — только на рабочей машине.
Хватает выгрузки дерева из git, нативные модули не нужны (`--ignore-scripts`):

```bash
L=<lint-dir>; rm -rf "$L"; mkdir -p "$L"
git archive HEAD controller web | tar -x -C "$L"
(cd "$L/controller" && npm ci --ignore-scripts && npm run lint)   # 0 errors; предупреждения — апстрима
(cd "$L/controller" && npm run gen:schemas)
diff -q "$L/web/lib/schemas.generated.ts" web/lib/schemas.generated.ts && echo SCHEMAS-SAME
```

Линтеру хватило бы `controller`; `web` выгружается ради зеркала схем:
`npm run gen:schemas` пишет `../web/lib/schemas.generated.ts` из
`controller/src/schemas/*.ts`. Тот же дифф делает CI апстрима
([lint.yml](../../.github/workflows/lint.yml), «Verify schema mirror is up to
date»). Расхождение — скопировать сгенерированный файл в репозиторий и закоммитить
отдельно (`fix(web): зеркало схем …`); руками зеркало не правится.

Замер 30.09 (v1.8): `npm ci` 48 с, линтер 30–130 с, `node_modules` ~300 МБ — каталог
после прогона удалить.

## Проверка

Настройки станции лежат в томе `state/` и пересоздание контейнера переживают, но
проверять после выкатки всё равно стоит: молчаливая потеря персоны выглядит как
«ведущий стал другим», а настройки форка без своего кода (образ не тот) — как
откат поведения. Чтение обратно — по LAN, снаружи `/api/settings` закрыт:

```bash
curl -su "$ADMIN_USER:$ADMIN_PASS" http://<station-host>:7700/api/settings | python3 -c '
import json, sys
v = json.load(sys.stdin)["values"]
print("personas:", [p["name"] for p in v["personas"]])
print("queue:", v.get("queue"))                       # C03: нет ключа — образ без форка
print("noRepeatWindow:", v["llm"].get("noRepeatWindow"))
print("tts.fallback:", v["tts"].get("fallback"))'
```

На живом эфире (из `<stack-dir>`):

- **очередь** — `state/queue.json`: в `upcoming` до `queue.lookahead` элементов,
  `sent: true` ровно у одного, заказ (`requestedBy`, без `aiPicked`) — перед
  несданными авто-пиками:
  `sudo python3 -c "import json; [print(i.get('sent'), i.get('aiPicked'), i.get('requestedBy'), i['track']['title']) for i in json.load(open('state/queue.json'))['upcoming']]"`;
- **подводки на стыке** — `sudo docker logs sub-wave-controller` с `link` между
  треками и без `Seam link failed`;
- **окно артиста** — `pick.artistGuard` с `"cause":"window"` в
  `state/logs/events-<дата>.jsonl`;
- **запрет подмены TTS** — при сорвавшемся движке `TTS failed` без `falling back`;
- **погода** — `duration` у `/now-playing` в `sudo docker logs sub-wave-caddy` не
  упирается в 10 с;
- **правило Folder** — на вкладке Blocked нет строки «N tracks have no real path».

## Обновление апстрима

0. **Репетиция — до релиза апстрима.** Сеть — руками: `git fetch upstream --tags`,
   затем:
   ```bash
   bash station/tools/merge-preview.sh              # upstream/develop против HEAD
   bash station/tools/merge-preview.sh vX.Y.Z       # или против тега
   ```
   [merge-preview.sh](../tools/merge-preview.sh) печатает файлы, которые дадут
   конфликт, и для каждого — коммиты апстрима после общей базы; рабочее дерево, индекс
   и ref-ы не трогает (`git merge-tree --write-tree`), код 1 — конфликты есть. Эти
   коммиты читаются заранее: где правка апстрима задевает смысл фичи, правило слияния
   записывается в раздел фичи сразу (пример — C03, «Длительности добора — к эфиру»), а
   не выясняется посреди конфликта. Прогон 2026-10-09 против `develop` от 2026-10-05 —
   шесть файлов: `queue.ts`, `queue/pure.ts`, `picker/scope.ts`, `PlayerCore.tsx`,
   `useMediaSession.ts`, `usePlayer.ts`.

Новая версия апстрима вливается в `main` слиянием, не rebase: ветка опубликована.

```bash
git fetch upstream --tags
git switch -c upgrade-X.Y.Z main
git merge vX.Y.Z
```

1. **Конфликты.** Для каждого файла — `git log --oneline v<прежняя>..vX.Y.Z --
   <файл>` и чтение этих коммитов апстрима. Разрешать так, чтобы осталось поведение
   апстрима **и** смысл фичи; смысл — разделы этого документа: что фича делает, зачем
   и какие инварианты держит. Апстрим сделал то же сам — наш код снимается, вердикт
   «апстрим сделал» со ссылкой на его коммит.

   **`show-filter.ts` git сливает как двоичный.** В нём литеральный NUL (апстрим,
   шаблонная строка ключа), а NUL в первых 8000 байтах — для git признак двоичного
   файла. Строка `diff` в [.gitattributes](../../.gitattributes) показывает его дифф
   текстом, но слияние идёт как двоичное и при `merge=text` (проверено, git 2.55):
   правка с обеих сторон — `CONFLICT (content)` **без маркеров**, в файле — наша
   версия, `git merge-file` отказывает («Cannot merge binary files»). Тогда — через
   три версии из индекса, NUL на время слияния заменён маркером:
   ```bash
   f=controller/src/music/show-filter.ts; t=$(mktemp -d)
   for s in 1 2 3; do git show ":$s:$f" | sed 's/\x00/@NUL@/g' > "$t/$s"; done  # база, наша, апстрим
   grep -c '@NUL@' "$t"/*                       # по 1: маркер стоит только на месте NUL
   git merge-file -L ours -L base -L vX.Y.Z "$t/2" "$t/1" "$t/3"   # маркеры — в $t/2
   # разрешить конфликты в $t/2, затем:
   sed 's/@NUL@/\x00/g' "$t/2" > "$f" && git add "$f" && rm -rf "$t"
   ```
   Правка только с одной стороны сливается сама — рецепт нужен лишь при конфликте.
   Апстриму стоит предложить `\u0000` вместо литерального NUL (не предлагалось) —
   тогда не нужны ни рецепт, ни строка в `.gitattributes`.
2. **Миграции `library.db`.** Сверить новые блоки `userVersion < N` в
   `music/library-db/schema.ts`: наша колонка `path` номера не занимает, но заведёт
   апстрим свою колонку `tracks.path` — его `ALTER TABLE` упадёт на базе станции на
